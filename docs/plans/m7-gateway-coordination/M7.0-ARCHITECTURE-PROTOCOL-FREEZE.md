# M7.0 — Architecture, Protocol & Configuration Freeze

**Status:** FROZEN / IMPLEMENTATION UNBLOCKED.

## Objective

Resolve the current source prerequisites before production implementation so that M7 does not encode unsafe retry, lifecycle or authority semantics into a large Gateway refactor.

## A. Protocol spike

Using the exact Gateway lockfile/dependency graph, build a minimal test harness that records:

1. the upstream request identity visible to `ServerHandler::call_tool`;
2. how `notifications/cancelled` is surfaced;
3. whether dropping an upstream response future cancels server work;
4. how child `Peer::call_tool` assigns/exposes request IDs;
5. whether child cancellation can be propagated explicitly;
6. progress token transport in both directions;
7. resource list/read APIs and pagination;
8. list-changed notification behavior;
9. behavior across the supported MCP protocol versions.

The spike belongs in test/dev code or a disposable fixture, not production architecture. Record exact rmcp version and selected protocol behavior in an ADR.

### A.1 Current result — VERIFIED

The locked dependency is `rmcp 3.4.0`. Seven permanent integration tests under Gateway `tests/m7_protocol_spike.rs` pass together with the original six Gateway tests; full fmt/check/Clippy/test gates pass.

See [RMCP-PROTOCOL-SPIKE.md](RMCP-PROTOCOL-SPIKE.md) for evidence.

Frozen consequences for M7.1:

- replace the current outer timeout pattern with a Gateway-owned cancellable child-request handle;
- record `DISPATCHED` before handing the child request to rmcp;
- a timeout/cancel/disconnect after dispatch may request cooperative child cancellation but remains `OUTCOME_PENDING` until a trustworthy terminal result is observed;
- loss of transport/terminal evidence after dispatch becomes `OUTCOME_UNKNOWN`;
- neither pending nor unknown mutation outcome is automatically replayed;
- protocol request IDs and progress tokens are correlation data, not authority;
- the initial M7 coordinator keeps the current 2025-11-25 legacy child lifecycle;
- 2026-07-28 Discover lifecycle is a separate explicit migration, not an incidental refactor;
- progress forwarding requires a real child ClientHandler plus upstream↔child token mapping;
- resource aggregation can be implemented on rmcp 3.4.0 without a dependency upgrade.

## C. State ownership

Freeze four independent generations:

- `catalog_generation` — exposed route/resource catalog;
- `profile_generation` — active routable policy surface;
- `child_generation(child)` — one child process/transport incarnation;
- `drain_generation` — one drain episode.

A request captures relevant generations at admission/dispatch for telemetry. Generation identity cannot authorize retries or signal processes.

## D. Config migration

### D.1 Current result — FROZEN

ADR 0031 freezes the policy/migration boundary.

Managed layout:

```text
runtime/gateway/
  gateway.yaml
  servers.d/
    *.yaml
```

`servers.d/*.yaml` remains child launch authority. M7 coordination policy is kept in separate `gateway.yaml` so the existing deny-unknown-fields child parser is not overloaded with M7-only policy.

Gateway policy schema v1 owns:

- active profile;
- global/queue/default-child scheduler limits;
- class-default concurrency;
- drain defaults;
- payload/artifact budgets;
- named profiles;
- per-child concurrency/restart policy;
- per-tool class/profile/concurrency policy.

Frozen scheduler defaults from ADR 0028:

```text
global_active = 16
global_queue = 64
queue_wait_ms = 30000
default_child_active = 4
read = 4
mutation = 1
long-running = 1
control = 1
```

Frozen restart defaults from ADR 0029:

```text
max_attempts = 3
stability_window_ms = 30000
backoff = 500 ms exponential, max 30000 ms
circuit cooldown = 60000 ms
half_open_attempts = 1
```

Fleet host schema v2 gains explicit Gateway policy inputs and renders a deterministic Fleet-owned `gateway.policy` surface at `gateway/gateway.yaml`. Studio reconciliation must snapshot, replace, verify and compensate that surface together with existing managed config.

Compatibility rule:

- Fleet 0.3.0 handles explicit host-schema migration;
- Gateway 0.2.0 declares support for Gateway policy schema v1;
- Gateway 0.2.0 derives `gateway.yaml` from the parent of the trusted `--config-dir`; absence is explicit `legacy_compat` mode and cannot be reported as M7 strict readiness;
- a host with active policy schema v1 cannot activate/downgrade to Gateway 0.1.x, because silently ignoring `gateway.yaml` would disable M7 safety;
- staged Gateway compatibility is proven by side-effect-free `--capabilities-json`, not by semver alone;
- unknown policy fields/references fail closed;
- profile expansion never exceeds the child launch allowlist.

## E. Drain control surface

### E.1 Current result — VERIFIED for M7.0 viability

P-06 is resolved at the architecture/viability layer by ADR 0027.

The frozen control path is a private local Unix-domain socket at `runtime/gateway/control/gateway.sock`, derived only from trusted runtime/config roots. Studio is a requester/observer; Gateway in-memory state is authoritative for `RUNNING -> DRAINING -> DRAINED`.

The wire protocol is closed and typed with `status | drain | resume | reload`, one UTF-8 JSON object per LF-framed request/response connection. Process stop, SQLite state, signal files and TCP control ports are not drain authority.

Gateway permanent probe `tests/m7_control_socket_viability.rs` passes 3/3, including newline-framed typed round-trip behavior, stale-path rejection and server-owned drain generation. Full Gateway fmt/check/Clippy/test gates pass with 16 tests total.

Production control server/client and Studio destructive-update/reconciliation integration remain M7.2 work; the viability result must not be interpreted as implementation completion.

## F. Tool classification

Classification is explicit trusted configuration, not name heuristics.

Required classes:

- `read`
- `mutation`
- `long-running`
- `control`

Every exposed tool must have a classification before M7 strict mode can become default. ADR 0031 freezes unknown classification as fail-closed: an unclassified tool is not routable.

Profile membership and class are independent: a mutation can be present in `develop`, but still receives mutation drain/retry semantics.

## G. Filesystem v2 schema freeze

### G.1 Current result — FROZEN

ADR 0030 freezes Filesystem 0.2.0.

Content revision:

```text
revision = "sha256:" + lowercase_hex(SHA-256(exact_file_bytes))
```

Frozen tools:

- `file_metadata`;
- `read_text_file` with revision metadata;
- `read_text_file_range(path,start_byte,max_bytes)`;
- literal bounded `search_text`;
- `write_text_file.expected_revision`;
- deterministic `patch_text_file` using ordered, non-overlapping UTF-8 byte-range edits.

Replacing an existing file requires `overwrite=true` plus `expected_revision`; missing revision fails with `EXPECTED_REVISION_REQUIRED`, mismatch with `STALE_REVISION`.

Patch coordinates use zero-based UTF-8 byte offsets so search/range/patch share one coordinate system. No shell/editor scripts or free-form diff parser are accepted.

Mutation implementation must preserve cap-std confinement, serialize same-path in-process mutations, use sibling temp + sync + atomic rename, and re-hash the destination immediately before replacement. The contract explicitly does not claim a kernel-level CAS guarantee against an arbitrary non-cooperating external writer in the final check-to-rename instruction window.

- full `tunnel-client` is installed alongside it for bounded diagnostics/preflight;

- liveness, readiness, MCP discovery health and control-plane poll health remain separate states;
- both assets must come from and verify against the same upstream release metadata/checksum manifest;
- existing M5 versioned activation, launch identity, config/credential preservation and rollback authority remain intact.
