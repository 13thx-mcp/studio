# M5.6 — Installed / Available / Running / Desired Inventory and Drift API

## Goal

Expose trustworthy component version/inventory state through Studio before allowing active update operations.

## Prerequisites

- M5.1–M5.5 merged.
- Read `COMMON.md` and prior handoffs.

## Scope

Implement a backend inventory service that can determine, for each known component:

- installed version;
- running version when observable;
- desired version if configured;
- latest available version from the trusted provider;
- platform/architecture;
- installed path;
- provider/repository identity;
- update available state;
- drift state;
- source-present versus runtime-only host mode;
- last check timestamp/result for the current process lifetime.

## Installed version sources

Use component-specific trusted mechanisms, for example:

- Rust MCP/service binary `--version` where supported;
- release/install metadata if that is more authoritative;
- tunnel-client binary `--version` plus active `current` release identity;
- Fleet `VERSION` in deployed runtime bundle.

Do not infer installed version from source `Cargo.toml` on runtime hosts.

## Running version

Where the currently running process can be tied to an installed artifact, report running identity separately. If the identity cannot be proven, report `Unknown` rather than assuming installed == running.

## Desired version

Introduce the minimum server-side desired-version policy needed for M5. Do not implement unattended auto-update policy. Desired version may initially be explicit/pinned/latest-stable depending on the architecture selected in M5.1, but semantics must be deterministic and documented.

## Drift derivation

Derive tested states such as:

```text
CURRENT
UPDATE_AVAILABLE
INSTALLED_RESTART_REQUIRED
DRIFTED
UNKNOWN
BROKEN
```

Examples:

- installed == running == desired == latest → CURRENT;
- latest newer but desired remains current → UPDATE_AVAILABLE or policy-specific equivalent;
- installed newer than running after staged service replacement → INSTALLED_RESTART_REQUIRED;
- installed differs from desired unexpectedly → DRIFTED;
- installed binary missing/corrupt → BROKEN.

## API

Add read-only API direction, for example:

```text
GET  /api/updates
GET  /api/updates/{component}
POST /api/updates/check
GET  /api/fleet
GET  /api/fleet/drift
```

Exact routes can vary if consistent with existing API conventions.

`POST /check` may perform remote release metadata checks, but must not download/install artifacts.

## Realtime

Add typed invalidation/progress events if useful so the UI can refresh inventory without polling aggressively. Keep payloads browser-safe and avoid exposing internal secret-bearing URLs/headers.

## Security requirements

- Known component IDs only.
- No arbitrary file/version probe path from browser input.
- Release provider comes from trusted component policy.
- Broken/missing runtime must not cause Studio crash.
- Source tree presence must not change installed-version truth.

## Tests

Cover:

- missing binary;

- Runtime-only inventory works with source tree absent.
- Drift states are deterministic and tested.

## Out of scope

- update apply/rollback;
- unattended policy;

## Implementation evidence — 2026-09-17

Implemented directly on the canonical `feat/m5-runtime-distribution` integration branch after M5.5. No active update/apply/rollback behavior was introduced.

### Inventory truth model

- New module: `src/update/inventory.rs`.
- `InventoryService` keeps installed, running, desired, and latest identities separate and derives M5.1 `DriftState` from those dimensions plus installation health.
- Installed identity is runtime-artifact authoritative only:
  - Filesystem/Git/Exec/Gateway/Blender: catalog-derived flat binary `--version`;
  - Studio: `runtime_root/studio/mcp-studio --version`;
  - Fleet: deployed `runtime_root/fleet/VERSION`;
  - tunnel: confined `runtime_root/tunnel-client/current` plus `tunnel-client-runtime-cloudflared --version`, with release-directory version agreement when `current` resolves to `v<version>`.
- Version probes run with an empty environment and five-second timeout and require strict semantic-version output. Missing/malformed deployed artifacts produce `BROKEN`; source manifests/Git HEAD are never consulted.
- `source_present` / `HostMode::{SourcePresent, RuntimeOnly}` is informational only and checks the trusted source root for the catalog repository directory. Source presence cannot change installed identity.
- Running identity is a separate `RunningIdentityProvider`. Studio can prove its own running package version. MCP/tunnel versions remain `None` when they cannot be proven rather than assuming installed == running. Fleet is a non-running control bundle: drift derivation uses installed identity as effective runtime state without serializing a fake running version.

### Desired/latest/check semantics

- New server-side `[updates]` config owns `source_root`, `bin_root`, `runtime_root`, and optional `[updates.desired]` semantic-version pins.
- Without a desired pin, M5 manual policy is preserve-current (`desired = installed`); latest-stable is visibility only and does not silently become desired or trigger an update.
- Default roots remain backward compatible for both source-checkout and runtime-only launch directories by finding the nearest conventional ancestor containing `bin/` and `runtime/`. Explicit configured paths override detection.
- `POST /api/updates/check` performs trusted release metadata lookup only. Each component receives a process-local check timestamp/result and latest version.
- Remote/provider failure does not remove local installed identity or a previously known latest version. Browser-visible errors are sanitized categories/statuses (`provider_unreachable`, `http_<status>`, `malformed_release_metadata`, etc.) rather than raw provider text/URLs.
- No M5.6 state is persisted; persisted history/audit remains M6 scope.

### Browser-safe API / realtime contract

Routes:

```text
GET  /api/updates
GET  /api/updates/{component}
POST /api/updates/check
```

- Unknown component IDs fail closed with 404.
- `POST /check` retains same-origin browser mutation protection even though it is read-only with respect to runtime state.
- Successful checks publish typed `updates_changed` invalidation so M5.11 can refresh inventory without aggressive polling.
- Public `InventoryView` fields are: component/display/class/provider, typed platform, host mode/source presence, installed/running/desired/latest versions, `update_available`, installation health, drift, and last-check timestamp/status/sanitized error.
- Internal `InventoryEntry` additionally retains trusted install path and repository owner/name for later orchestration. Those fields, release/download/checksum URLs, headers, binary paths, and secrets are deliberately absent from browser DTOs.

### M5.7 carry-forward contract

M5.7 can consume `InventoryService`/M5.1 version dimensions as the pre-transaction view, but it must not treat an unknown running version as synchronized. Before activation it must revalidate the staged artifact per the M5.5 handoff and snapshot the affected component's pre-update lifecycle state. On successful activation it owns updating/reconciling installed and desired identity and proving the restarted running identity where applicable; stopped MCPs must remain stopped. On failure it owns rollback preparation/activation and must leave subsequent inventory capable of distinguishing `DRIFTED`, `INSTALLED_RESTART_REQUIRED`, `BROKEN`, or `UNKNOWN`. M5.7 must not derive any of those states from source presence.
