# M5.10 — Studio Self-Update and External Supervisor Contract

## Goal

Define and implement a safe Studio self-update mechanism that stages/verifies a new Studio release inside Studio but delegates process replacement to an external supervisor/launcher.

Studio must not blindly overwrite and kill its own running executable in-process.

## Prerequisites

- M5.1–M5.9 merged.
- M5.9A runtime reconciliation merged and its canonical runtime-binding contract is preserved.
- Read `COMMON.md` and prior handoffs.
- Inspect actual current Studio runtime launch method on Aira before choosing the supervisor contract.

## Current runtime contract

Studio runtime lives under:

```text
runtime/studio/
├── mcp-studio
├── studio.toml
├── data/
└── web/dist/   # or packaged equivalent depending on release activation design
```

Published Studio releases contain the matching backend binary and `web/dist`.

## Scope

Implement a staged self-update protocol with an explicit external activation boundary.

Required phases:

```text
check release
→ download/verify/stage Studio package
→ validate backend binary + matching web/dist
→ prepare rollback package/path
→ persist pending self-update metadata
→ request external supervisor activation
→ current Studio exits gracefully or returns restart-required state
→ external supervisor swaps release / restarts Studio
→ new Studio starts
→ new Studio detects pending update
→ health/self-check
→ finalize success OR trigger rollback contract
```

## External supervisor

Initial macOS design should be compatible with `launchd` or a small trusted launcher process/script managed outside the Studio process.

Define clearly:

- who owns the Studio PID;
- who performs filesystem activation;
- who performs restart;
- where pending update metadata lives;
- how the new process proves it is healthy;
- how rollback is requested/performed;
- what happens if the host reboots mid-update.

Do not implement a general-purpose privileged command runner.

## Runtime layout options

Prefer a versioned release layout if it simplifies rollback, for example conceptually:

```text
runtime/studio/
├── current -> releases/vX.Y.Z
├── releases/
│   ├── vX.Y.Z/
│   └── vA.B.C/
├── studio.toml
└── data/
```

If preserving the current flat `runtime/studio/mcp-studio` layout, define equivalent atomic replacement + rollback guarantees.

Any durable layout change must update Fleet render/deploy behavior and documentation.

## State preservation

Self-update must preserve:

- `studio.toml`;
- registry/database state;
- host-local secrets/config references;
- logs according to policy;
- audit/update metadata;
- tunnel/Gateway/MCP runtime state unless explicitly coordinated.

Release archive must never overwrite these local state files.

## Web asset consistency

Backend and dashboard assets must be activated as one release unit. Never run backend vX with stale `web/dist` from an incompatible version and report success.

## API/UI semantics

Applying Studio update may return a durable transaction ID + `restart_required` / `activation_pending` rather than a synchronous success response.

After reconnect, the browser must be able to query the transaction and see whether:

```text
updated successfully
rolled back
activation pending
activation failed
rollback failed
```

## Tests

Cover with a fake/test launcher first:

- successful stage + activation handshake;
- new Studio startup finalizes pending update;
- startup health failure requests rollback;
- web/dist missing rejects package before activation;
- local config/data preserved;
- interrupted activation/reboot recovery semantics;
- stale pending update metadata;
- launcher unavailable;
- launcher returns failure;
- transaction status recoverable after process restart;
- rollback returns to previous Studio + web assets.

Add a controlled Aira smoke only after the fake-launcher integration tests are strong. Plan for reconnect explicitly.

## Security requirements

- Launcher path and allowed operations are server-side fixed policy.
- No browser-provided executable/command/arguments.
- Pending update metadata is integrity/ownership protected as practical.
- Activation path cannot escape Studio runtime root.
- Never expose environment secrets to launcher logs/API.
- Avoid privilege escalation; run with minimum filesystem/process privileges required.

## Acceptance criteria

- Studio can fully stage and request activation of its own verified release.
- External supervisor contract is implemented/tested and documented.
- New process can finalize or rollback pending update deterministically.
- Local state/config survives update and rollback.
- Backend + web assets activate as one unit.
- Reconnect transaction status is recoverable.
- Full backend/UI gates and controlled self-update smoke pass.

## Out of scope

- unattended self-update policy;
- remote multi-host rollout;
- OS service support beyond the initial macOS contract unless trivial.

## Completion handoff

Document the final runtime layout, launchd/launcher interface, pending-update persistence model, activation/rollback ownership, and API state M5.11 will surface.
## Implementation evidence — 2026-09-19

Implemented on `feat/m5-runtime-distribution` after M5.9A. Aira inspection found the deployed legacy layout `runtime/studio/{mcp-studio,studio.toml,data}` with no running `mcp-studio` process and no Studio launchd label, so M5.10 uses the plan-approved small trusted external launcher instead of assuming a service supervisor.

### Final contract

Studio `SelfUpdateManager` owns trusted release discovery/staging, candidate preparation, durable journal, external handoff and startup finalization. Fleet `fleetctl studio-activate` owns process replacement, versioned release activation, replacement startup, target health proof and rollback.

The runtime layout is `runtime/studio/current -> releases/vX.Y.Z`; each release contains `mcp-studio` plus matching `web/dist`. `studio.toml` and `data/` stay outside release directories. The legacy flat `mcp-studio` remains first-migration/bootstrap rollback material, and Fleet source install becomes bootstrap-only once `current` exists.

Prepare reuses the trusted project release provider and M5.5 staging, requires matching backend plus `web/dist/index.html`, validates target semantic version, computes a bounded full-tree fingerprint, and persists a schema-versioned transaction under `runtime/studio/data/self-update`. Apply revalidates staging/source/candidate identity and accepts activation only from the deployed Studio executable.

Studio launches only the fixed deployed Fleet launcher with server-selected host ID, durable transaction ID and its own PID, returns `activation_pending`, then requests graceful shutdown. Fleet waits for that PID, promotes the candidate, atomically repoints `current`, launches the target with host-local `studio.toml`, and requires `/health` status/service/version to match. Failure after switching triggers versioned or legacy-flat rollback.

The journal survives restart and browser reconnect. Startup can finalize an externally activated or rolled-back transaction. Repeated apply can re-arm interrupted activation with a new source PID while preserving the originally persisted rollback identity. `rollback_failed` blocks a later self-update until repair.

### M5.11 handoff

M5.11 should treat Studio apply as asynchronous. `activation_pending`, `external_activating`, `health_verifying`, `completed`, `rolled_back`, `failed`, and `rollback_failed` are durable phases that may span browser disconnect/reconnect. The UI should retain the transaction ID and re-query `GET /api/update-transactions/{id}` after reconnect.
