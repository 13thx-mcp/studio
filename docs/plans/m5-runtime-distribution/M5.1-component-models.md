# M5.1 — Component, Release Provider and Update Domain Models

## Goal

Establish stable backend domain models and interfaces for release-based runtime management before any network download or activation logic is added.

## Read first

- `COMMON.md`
- current `src/config`, `src/registry`, `src/supervisor`, `src/tunnel`, API DTO patterns
- `mcp-server/fleet/fleet.toml` and `scripts/fleetctl.py` for existing component/release concepts
- current `ROADMAP.md` M5 section

## Scope

Design and implement typed models for at least:

- component identity;
- component class;
- release source/provider;
- semantic version identity;
- installed artifact identity;
- available release identity;
- platform identity;
- update/drift state;
- update transaction state;
- rollback metadata;
- component-specific runtime/update policy.

Recommended component classes:

```text
McpBinary
Service
ControlBundle
UpstreamRuntime
```

Expected current mappings:

```text
filesystem → McpBinary
git        → McpBinary
exec       → McpBinary
gateway    → McpBinary
blender    → McpBinary
studio     → Service
fleet      → ControlBundle
tunnel     → UpstreamRuntime
```

## Required contracts

Define a server-side component catalog/policy source. Browser requests must identify a known component ID only; they must not provide repository URLs, download URLs, executable paths, or checksum locations.

Model version dimensions separately:

```text
installed_version
running_version
desired_version
latest_version
```

Model update transaction states explicitly. Avoid stringly typed state machines where practical.

Provider abstraction should support future implementations without exposing provider-specific transport details to higher layers. At this stage it may be a trait/interface with read-only methods only.

Suggested conceptual methods:

```text
component(id)
list_components()
provider_for(component)
installed_identity(component)
```

Release-provider read interface direction:

```text
latest_release(component)
release(component, version)
select_asset(release, platform)
checksum_manifest(release)
```

Do not implement remote HTTP behavior yet beyond minimal compile/test stubs if needed.

## Persistence boundary

M5.1 does not introduce SQLite. Keep models serializable where useful, but do not prematurely persist transient update state to ad-hoc files unless required by the existing architecture.

## API boundary

Do not add the full update API yet. It is acceptable to add internal DTOs/types needed later, but M5.6 owns public inventory/drift endpoints.

## Security requirements

- Unknown component IDs fail closed.
- Provider/repository ownership is server-side policy.
- No arbitrary URL/path fields in browser-facing mutation DTOs.
- Versions must be parsed/validated, not compared lexicographically.
- Component install roots must derive from trusted host/runtime config.

## Tests

Add unit tests covering at least:

- component catalog contains expected current components;
- unknown component rejected;
- component-class mapping;
- semantic version parsing/order;
- update-state serialization if exposed;
- drift-state derivation for representative version combinations;
- provider selection by trusted component config;
- browser-safe DTOs omit internal URLs/paths/secrets where not required.

## Documentation

If introducing a durable module/interface boundary, update `docs/architecture.md` and add an ADR if the provider abstraction or update-state ownership is a long-term architectural decision.

## Acceptance criteria

- Current code compiles with typed component/release/update models.
- Component catalog represents all current managed/release components.
- No network download or activation occurs in this submilestone.
- Version/drift/update states have deterministic tested semantics.
- Trusted policy versus browser input boundary is explicit in code/tests/docs.
- Full backend quality gates pass.

## Out of scope

- GitHub API calls.
- downloading archives.
- checksum verification.
- runtime activation/restart.
- rollback execution.
- UI.

## Completion handoff

State the final module locations/types/traits and any model decisions M5.2 must preserve.

### Final M5.1 backend contract

- Module: `src/update/mod.rs`.
- Closed identity: `ComponentId` (`filesystem`, `git`, `exec`, `gateway`, `blender`, `studio`, `fleet`, `tunnel`).
- Classification: `ComponentClass::{McpBinary, Service, ControlBundle, UpstreamRuntime}`.
- Trusted policy: `ComponentCatalog`, `ComponentPolicy`, `ReleaseSource`, `ReleaseProviderId`, `InstallTarget`, `UpdateChannel`, `RestartPolicy`.
- Trusted roots: `HostRuntimeRoots`; catalog-derived install paths preserve flat `bin_root` MCP binaries and `runtime_root/<component>` bundles.
- Version/platform identity: `Version` backed by `semver`, plus `Platform`, `OperatingSystem`, `Architecture`. Platform normalization remains M5.4 scope.
- Artifact/release identity: `InstalledArtifactIdentity`, `AvailableRelease`, `ReleaseAsset`.
- State: `VersionDimensions`, `InstallationHealth`, `DriftState`, `UpdateState`, `UpdateTransaction`, `RollbackMetadata`.
- Provider interfaces: async read-only `ReleaseProvider` and `InstalledIdentityProvider`; M5.1 provides no HTTP implementation.
- Browser boundary: `ComponentRequest` accepts only a typed known component ID and rejects unknown fields; `ComponentView` omits repository/download/checksum URLs, install paths, binary names, and secrets.
- Unknown component IDs fail closed through `StudioError::UnknownComponent`.

### Deterministic drift precedence

1. broken installation health → `BROKEN`;
2. unknown health or incomplete installed/running/desired identity → `UNKNOWN`;
3. installed != desired → `DRIFTED`;
4. running != installed → `INSTALLED_RESTART_REQUIRED`;
5. latest > installed → `UPDATE_AVAILABLE`;
6. otherwise → `CURRENT`.

### M5.2 carry-forward contract

M5.2 must preserve `ComponentCatalog` as the repository/provider/install authority, use `Version::cmp_precedence` / `Version::is_newer_than` for release precedence (build metadata must not make a release newer), and implement the async `ReleaseProvider` interface without accepting caller-selected repository/download/checksum URLs. It must not move MCP artifacts out of the flat `bin_root` layout or introduce activation/download behavior outside the later staged transaction milestones.
