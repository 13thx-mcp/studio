# M5.9 — Fleet Control Bundle Update with Host-Profile Preservation

## Goal

Implement safe update of the architecture-independent `mcp-fleet` runtime control bundle without overwriting host-local profiles, secrets, or generated runtime config.

## Prerequisites

- M5.1–M5.8 merged.
- Read `COMMON.md` and prior handoffs.
- Current Fleet release package contract must be inspected before implementation.

## Current Fleet release contract

```text
mcp-fleet-vX.Y.Z.tar.gz
SHA256SUMS.txt
```

Current release bundle contains generic control content such as:

```text
VERSION
fleet.toml
README.md
scripts/fleetctl.py
hosts/mirin.example.toml
```

It intentionally does not ship `hosts/aira.toml`.

## Runtime contract

Current deployed Fleet control lives under:

```text
runtime/fleet/
```

Host-local active profile must be preserved across update.

## Scope

Implement release check/stage/activate/rollback for Fleet control bundle.

Required behavior:

- query/stage verified Fleet release through common provider/staging layers;
- validate Fleet package structure/version;
- identify generic files versus host-local mutable state;
- preserve active `hosts/<host>.toml` exactly unless a validated schema migration is required;
- preserve generated runtime configs outside the Fleet bundle;
- validate new Fleet schema compatibility before activation;
- atomically activate updated generic control files where practical;
- provide rollback to prior Fleet version;
- update inventory/drift state.

## Host profile preservation

Never blindly replace the active host profile with an example from the release archive.

The update process should treat host profile as local state, not release payload.

If `fleet.toml` schema or host profile schema changes:

- detect schema version;
- validate compatibility;
- use an explicit migration path;
- back up local profile before migration;
- fail without activation if migration cannot be proven safe.

## Render validation

Before final success, use the updated Fleet tooling/schema to validate or dry-run:

```text
Gateway runtime config
Studio runtime config
Tunnel runtime config
```

Do not activate generated config changes automatically unless the update design explicitly owns and verifies them.

## Update ownership

Be clear whether Studio executes Fleet logic internally, invokes deployed `fleetctl`, or treats Fleet as data/control bundle only. Avoid circular ownership where Fleet updates Studio while Studio simultaneously updates Fleet without transaction coordination.

## Tests

Cover:

- successful architecture-independent Fleet update;
- host profile preserved byte-for-byte;
- example host profile does not overwrite active profile;
- invalid Fleet VERSION/schema rejected;
- malformed bundle rejected;
- checksum failure never touches runtime;
- render validation failure prevents success;
- local profile backup/migration behavior;
- rollback restores previous Fleet generic files and preserves host profile;
- runtime-only host with no source repo.

## Security requirements

- Trusted Fleet release provider only.
- Host-local profile path is server-controlled.
- Release cannot write arbitrary paths outside Fleet runtime root.
- Config render/validation errors fail closed.
- No secrets included in diagnostic/update response.

## Acceptance criteria

- Fleet can update from published verified bundle on a source-less host.
- Active host profile survives unchanged in the normal compatible case.
- Schema incompatibility is detected before destructive activation.
- Rollback works without losing host identity/config.
- Updated Fleet tooling can validate the current runtime configuration model.
- Backend/Fleet gates and runtime smoke pass.

## Out of scope

- Studio binary self-update;
- unattended update scheduling;
- central multi-host rollout.

## Completion handoff

Document Fleet update ownership, profile migration contract, generic-versus-local file boundary, and any launcher/runtime dependency M5.10 should know.

## Implementation evidence — 2026-09-18

Implemented directly on the canonical feat/m5-runtime-distribution branch after M5.8. No separate M5.9 branch was created and no Fleet source-repository change was required.

### Fleet update ownership

M5.9 treats Fleet as an architecture-independent data/control bundle managed transactionally by Studio. Studio does not invoke fleetctl deploy-control to let Fleet replace itself, and Fleet does not update Studio as part of this transaction.

The published 13thx-mcp/fleet release workflow was re-verified. A release contains exactly the generic control content:

- VERSION
- fleet.toml
- README.md
- scripts/fleetctl.py
- hosts/mirin.example.toml

plus the architecture-independent mcp-fleet-vX.Y.Z.tar.gz and SHA256SUMS.txt release assets.

The deployed Aira runtime was also inspected. runtime/fleet currently contains fleet.toml, README.md, scripts/fleetctl.py and hosts/aira.toml but no VERSION. This is a legacy deploy-control shape, while the release bundle contains VERSION. M5.9 therefore supports a controlled repair update from a version-unidentified legacy bundle instead of inferring installed version from source Git.

### Generic versus local boundary

New module: src/update/fleet.rs / FleetUpdateManager.

Release-owned generic files are the five paths above. Host-local state is:

- exactly one non-example hosts/<host>.toml active profile;
- optional regular files below state/.

M5.9 rejects unexpected top-level runtime entries, symlinks, special entries, multiple active profiles, excessive local-state file count or size, and invalid host identity/root coordinates. The release example profile is copied first as generic content and the active local profile is copied afterward under its original filename, so an example can never overwrite the active profile.

The active profile and optional state files are retained as private in-memory transaction state only; their bytes, permission bits, paths and contents are never exposed by the update DTO. Candidate activation preserves the local file permission bits as well as contents.

### Schema and migration contract

Current compatible schemas are explicit:

- Fleet fleet.toml schema_version = 2
- active/example host schema_version = 1

The active filename must equal <host_id>.toml and its bin_root/runtime_root must canonicalize to Studio's trusted update roots.

M5.9 intentionally implements no automatic schema migration. Any other Fleet or host schema fails before destructive activation. A future schema migration must have a separately reviewed versioned migrator and durable profile backup; silent rewriting is prohibited.

For ordinary compatible updates, the previous complete runtime/fleet directory itself is the rollback/profile backup until post-activation validation succeeds.

### Prepare/staging and TOCTOU contract

Fleet preparation reuses the trusted 13thx release provider, the architecture-independent M5.4 asset resolver and M5.5 checksum/archive/package validation.

In addition to the common StagedArtifact identity/executable SHA-256, Fleet prepare fingerprints all generic control files:

- VERSION
- fleet.toml
- README.md
- scripts/fleetctl.py
- hosts/mirin.example.toml

Apply reloads the server-owned ready staging transaction and requires both the common staging fingerprint and all Fleet generic-file hashes to match immediately before candidate construction. It also re-walks the staged package and requires the exact five-file release set; extra files, links or unsupported entries fail closed. Tampering with either fleetctl.py or non-executable generic metadata therefore fails before activation.

If an installed VERSION exists, the target must be newer by semantic-version precedence. If VERSION is absent but a valid local Fleet runtime/profile exists, an explicit trusted target is allowed as a legacy repair transaction.

### Candidate and render validation

Studio constructs a complete sibling candidate from verified release generic files and then copies the active host profile/state byte-for-byte.

Before activation it validates schema/root identity and runs the staged candidate's own tooling with fixed server-generated arguments:

- render-gateway --host <host> --check
- render-studio --host <host> --check
- render-tunnel --host <host> --check

Each command uses python3, a minimal fixed PATH, PYTHONDONTWRITEBYTECODE=1 and a 15-second timeout. The checks are read-only. M5.9 never auto-writes Gateway, Studio or tunnel generated runtime config.

The same checks run again from the activated bundle before success and from the restored prior bundle before rollback is accepted.

### Activation, rollback and interruption recovery

Activation uses sibling directories below trusted runtime_root:

- .mcp-studio-fleet-candidate-<transaction>
- .mcp-studio-fleet-rollback-<transaction>
- .mcp-studio-fleet-failed-<transaction>

After candidate validation, active runtime/fleet is renamed to the rollback directory and the candidate is renamed to runtime/fleet on the same filesystem. Success requires:

- target VERSION matches;
- active host profile bytes are unchanged;
- optional local state bytes are unchanged;
- supported schema/root identity still holds;
- activated Fleet render checks pass.

Only after those checks does Studio remove rollback material and update process-local desired inventory.

Post-activation validation failure quarantines the candidate, restores the complete prior runtime directory, rechecks the previous optional VERSION identity, verifies profile/state byte equality and runs the old Fleet render checks. Failure to prove restoration becomes rollback_failed.

At manager startup stale pre-activation candidate/failed directories are removed. If runtime/fleet is absent and exactly one finalized Fleet rollback directory exists, it is restored. Ambiguous finalized rollback material is not guessed.

### API and inventory integration

The existing browser-safe update API remains unchanged:

- POST /api/updates/fleet/prepare
- POST /api/updates/fleet/apply
- GET /api/update-transactions/{id}

Fleet requests accept only explicit version or server-generated transaction ID through the M5.7 request DTOs; no profile path, install path, URL or config destination can be supplied by the browser. Same-origin mutation protection and sanitized update errors continue to apply.

On successful activation InventoryService desired state is updated to the target Fleet version. The newly installed VERSION repairs the legacy Aira inventory state that M5.6 correctly reported as broken.

### M5.10 carry-forward

M5.10 must preserve the same ownership boundary for Studio self-update: release payload must not overwrite runtime config/state, the browser cannot provide executable/install/launcher paths, and post-activation success requires a component-appropriate proof. Unlike Fleet, Studio is the currently executing process, so M5.10 cannot reuse Fleet's in-process directory swap to replace/kill itself. It must honor COMMON.md and introduce/verify an external launcher or supervisor handoff contract before destructive self-update.

## Post-M5.9 incident follow-up — M5.9A

A later runtime incident exposed a gap intentionally left by M5.9's read-only render-validation contract: active generated Gateway/tunnel configuration can drift after Fleet update, and a helper/CLI override can mask stale canonical YAML.

M5.9 remains correct for release activation and local-profile preservation; it must not be retroactively changed to blindly rewrite generated config during Fleet update. The follow-on `M5.9A-runtime-reconciliation.md` owns:

- deterministic desired-versus-active runtime config comparison;
- split launch-path detection;
- managed-safe transactional repair with rollback;
- Gateway reload/tunnel restart only when required;
- exact child/tool-name catalog verification and catalog fingerprinting;
- explicit separation of local Gateway synchronization from unobservable remote-client refresh state.

M5.10 and later submissions must treat M5.9A as a prerequisite.
