# M5.3 — Official OpenAI tunnel-client Release Provider

## Goal

Integrate official `openai/tunnel-client` release metadata behind the common provider abstraction without forking or reimplementing the upstream product.

## Prerequisites

- M5.1–M5.2 merged.
- Read `COMMON.md` and prior handoffs.
- Inspect the current official release metadata/assets because upstream naming may evolve.

## Authority

Only official OpenAI tunnel-client releases are trusted for this component:

```text
https://github.com/openai/tunnel-client
```

Do not use the archived `13thx-mcp/tunnel-client` placeholder as an update source.

## Current known asset family

At v0.0.14 the relevant runtime-cloudflared assets include:

```text
tunnel-client-runtime-cloudflared-vX.Y.Z-darwin-amd64.zip
tunnel-client-runtime-cloudflared-vX.Y.Z-darwin-arm64.zip
SHA256SUMS.txt
```

The archive contains the runtime binary, cloudflared binary, manifest, licenses, and notices.

## Scope

Implement the tunnel provider using the same higher-level release-provider contract as project-owned components while keeping upstream-specific metadata encapsulated.

Required behavior:

- latest stable release discovery;
- explicit version discovery when requested;
- typed tag/version parsing;
- asset metadata enumeration;
- checksum manifest discovery;
- identify relevant runtime-cloudflared asset family;
- expose upstream/source identity distinctly from project-owned providers;
- preserve metadata needed later for extracted binary version validation.

## Existing reference behavior

`mcp-server/fleet/scripts/fleetctl.py` already has tested behavior for official tunnel release checks and updates. Reuse concepts/tests where appropriate rather than inventing incompatible semantics.

## Security requirements

- Trust only configured official OpenAI repository identity.
- HTTPS only.
- Do not follow arbitrary browser-provided URLs.
- Prerelease policy must be explicit.
- Provider metadata cannot overwrite host-local config/secrets.
- Release asset selection remains read-only at this submilestone.

## Implementation evidence — 2026-09-17

Canonical M5 integration history records this submission on `feat/m5-runtime-distribution` as `c4aaaf5` (`feat(update): implement M5.3 tunnel release provider`), directly after M5.2, without starting M5.4 or adding archive download/activation behavior.

### Provider implementation

- Concrete provider: `src/update/openai.rs`, exporting `OpenAiTunnelReleaseProvider` behind the unchanged M5.1 `ReleaseProvider` trait.
- Trusted authority remains `ComponentCatalog`: the provider accepts only `ComponentId::Tunnel` whose trusted provider/source is exactly `github_openai` + `openai/tunnel-client`. Caller-mutated `ComponentPolicy::source` values cannot redirect lookup.
- M5.2 and M5.3 now share `src/update/github_http.rs` for HTTPS-only Reqwest/Rustls behavior, 3-second connect timeout, 10-second request timeout, 1 MiB release-metadata cap, 256 KiB checksum-manifest cap, GitHub-controlled redirect policy, fixed User-Agent, and sanitized transport errors.
- Provider identity remains distinct through `ReleaseProviderId::OpenAiGitHub`; project-owned components remain `ReleaseProviderId::ThirteenthXGitHub`.
- No browser/API field was added for repository/base/download/checksum/executable/install URLs.

### Release/channel and asset semantics

- Latest lookup uses `https://api.github.com/repos/openai/tunnel-client/releases/latest` and verifies the returned release is not draft/prerelease.
- Explicit lookup accepts validated stable `Version` values and requests `releases/tags/v<version>`; semantic prerelease versions are rejected before network access.
- Release/asset IDs must be non-zero, asset names non-empty, release tags must use `v<semver>`, and every asset URL must remain under `https://github.com/openai/tunnel-client/releases/download/...`.
- Exactly one `SHA256SUMS.txt` is required at metadata level.
- Complete upstream asset enumeration is preserved in `AvailableRelease::assets`.
- Runtime candidates are recognized only as `tunnel-client-runtime-cloudflared-v<release>-<os>-<arch>.zip`. Evidence sidecars, source archives, and full-client ZIPs remain metadata but are not treated as runtime candidates.
- Runtime-cloudflared ZIPs with a release-version mismatch, malformed target identity, or duplicate target are rejected. At least one valid runtime-cloudflared ZIP must exist.
- Stable constants `TUNNEL_RUNTIME_ASSET_PREFIX` and `TUNNEL_RUNTIME_BINARY_NAME` both resolve to `tunnel-client-runtime-cloudflared`, preserving the identity needed for M5.4/M5.5 selection/staging/extracted binary version checks.
- `select_asset()` remains fail-closed with M5.4 ownership; no host OS/arch resolution was implemented.
- `checksum_manifest()` retrieves only the bounded manifest bytes; it does not verify archive content hashes.

### Official upstream verification

A live read-only check against the official GitHub API on 2026-09-17 confirmed latest stable `v0.0.14`, `draft=false`, `prerelease=false`, including:

- `SHA256SUMS.txt`;

### M5.4 / M5.5 carry-forward contract

M5.4 can rely on tunnel `AvailableRelease` containing a validated semantic version/tag, complete trusted upstream asset list, exactly one checksum-manifest URL, and a validated runtime-cloudflared ZIP family. It must normalize the host platform and deterministically select the matching archive without treating SPDX/license/source/full-client artifacts as candidates. M5.5 must fetch the selected ZIP, verify its `SHA256SUMS.txt` entry, safely extract ZIP paths/links, and verify the staged `tunnel-client-runtime-cloudflared` binary reports the release version before any activation.
