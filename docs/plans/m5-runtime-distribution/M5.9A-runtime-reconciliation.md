# M5.9A — Runtime Configuration Reconciliation & Catalog Repair

## Goal

Add a deterministic reconciliation layer between Fleet desired state and the live Studio / tunnel / Gateway runtime so configuration drift can be detected, explained, and safely repaired without depending on source checkouts.

This submission is an incident-driven follow-up to M5.9 and must land before M5.10.

## Incident / failure class

The runtime-host failure that motivates this work had two independent symptoms:

1. Fleet-generated runtime configuration was stale:
   - `runtime/tunnel-client/config.yaml` referenced the old source-tree Gateway path and source-tree `servers.d`;
   - `runtime/gateway/servers.d/exec.yaml` was out of sync with the active host profile;
   - `fleetctl render-tunnel --check` and `render-gateway --check` both reported drift.
2. Gateway locally knew the expected child catalog, while a connected client session temporarily exposed an older/incomplete tool catalog.

A launch path using `runtime/tunnel-client/run.sh` could mask the stale tunnel YAML by supplying a correct CLI override, while another launcher that consumed `config.yaml` directly could observe different behavior. Studio must treat this split-launch-path state as broken/drifted, not healthy.

## Design principle

Generated runtime configuration is a first-class desired-state surface.

Studio must distinguish:

```text
Fleet desired render
Active generated config
Live Gateway child catalog
Connected-client catalog freshness (when observable)
```

A matching process state alone is not sufficient proof of synchronization.

## Scope

Implement a `RuntimeReconciler` (name may change) that owns read/plan/apply/verify for Fleet-managed generated configuration.

Required surfaces:

- `runtime/gateway/servers.d/*.yaml`;
- `runtime/tunnel-client/config.yaml`;
- Studio runtime config emitted by Fleet;
- Gateway child/tool catalog derived from the active generated config.

The reconciler must work on runtime-only hosts and must not require Rust/Cargo, Node/pnpm, project source repositories, `target/`, or `node_modules/`.

## Desired-state authority

The desired render is derived only from:

- the deployed trusted Fleet control bundle;
- the single active server-selected host profile;
- trusted Studio update roots / runtime roots;
- server-owned component policy.

Browser/API callers must never supply:

- host-profile path;
- Gateway binary path;
- config destination;
- executable path;
- release URL;
- arbitrary Fleet arguments.

### Pure-render Fleet contract

M5.9A must add a side-effect-free Fleet render interface. Studio must not duplicate Fleet render logic in Rust.

The preferred contract is a Fleet CLI such as:

```text
fleetctl render-plan --host <host> --json
```

or an equivalent pure-render API that returns, without touching active runtime files:

- host identity;
- managed surface identifier;
- trusted relative destination below `runtime_root`;
- deterministic desired bytes or a lossless encoding of them;
- SHA-256 of those desired bytes;
- ownership class (`fleet_managed`);
- whether a Gateway reload or tunnel restart would be required if that surface changed.

The pure-render contract must cover at least Gateway `servers.d`, Studio runtime config, and tunnel config. The output must be deterministic for the same Fleet bundle + active host profile.

`render-*-check` remains a compatibility check, but M5.9A reconciliation must compare active bytes against desired bytes/hashes produced by this pure-render contract rather than reimplementing render semantics inside Studio.

## Reconciliation phases

Suggested model:

```text
CHECKING
  ↓
SYNCHRONIZED
  or
DRIFT_DETECTED
  ↓ plan
RECONCILE_READY
  ↓ apply
SNAPSHOTTING
  ↓
RENDERING
  ↓
VALIDATING
  ↓
RELOADING_GATEWAY        (only if Gateway config changed)
  ↓
RESTARTING_TUNNEL        (only if tunnel binding/config changed and it was running)
  ↓
CATALOG_VERIFYING
  ↓
SYNCHRONIZED
```

Explicit failures:

```text
UNMANAGED_CONFLICT
RENDER_FAILED
VALIDATION_FAILED
GATEWAY_RELOAD_FAILED
TUNNEL_RESTART_FAILED
CATALOG_MISMATCH
ROLLBACK_FAILED
CLIENT_REFRESH_PENDING
```

## Safe-write / ownership contract

Do not blindly overwrite a drifted file just because Fleet can render a replacement.

Before mutation, Studio must prove that every target is an expected Fleet-managed path below trusted runtime roots and is a regular non-symlink file (or an expected missing file).

### Persisted managed-state fingerprint

M5.9A must persist a server-owned managed-state record, conceptually under the Fleet runtime state area, containing at least:

```text
schema_version
host_id
generation
surface -> relative destination
surface -> last-known-managed SHA-256
catalog fingerprint/generation where available
```

The exact filename/schema may change, but it must be versioned, root-confined, browser-inaccessible as authority, and written atomically.

Reconciliation classification must be deterministic:

```text
active == desired
    → SYNCHRONIZED

active == last-known-managed && active != desired
    → MANAGED_SAFE_DRIFT

active != last-known-managed
    → UNMANAGED_CONFLICT
```

An expected missing file may be `MANAGED_SAFE_DRIFT` only when policy explicitly defines that surface as Fleet-managed and creation is safe.

For first adoption / legacy runtime, Studio must **not** assume every Fleet-looking file is managed. Legacy adoption must be one of:

- an explicitly recognized legacy-generated byte form whose provenance can be proven from trusted Fleet render semantics; or
- an explicit operator adoption action that records the current bytes as the managed baseline without silently rewriting them.

Unknown local edits must never be auto-adopted.

Any future secret-bearing or operator-owned fields must have explicit merge/preservation semantics. A full-file rewrite is permitted only for files whose complete contents are contractually Fleet-owned.

## Split launch-path validation

Studio must prove all supported launch surfaces resolve to the same authoritative runtime binding.

At minimum:

- tunnel YAML `main` MCP command;
- Studio/TunnelSupervisor launch contract;
- runtime helper script/launcher configuration where supported.

All must resolve to:

```text
<bin_root>/rust-mcp-gateway
--config-dir <runtime_root>/gateway/servers.d
```

### Launcher ownership boundary

Not every launch surface is automatically Fleet-owned.

For the current Aira runtime:

- `runtime/tunnel-client/config.yaml` is Fleet-generated and may be reconciled when managed-state ownership is proven;
- Studio/TunnelSupervisor configuration is server-owned and must be validated against the same binding;
- `runtime/tunnel-client/run.sh` currently injects a duplicate `--mcp.command` override but is **not** emitted by the Fleet renderer. M5.9A must therefore treat it as a validate-only launcher surface unless a separate managed ownership/fingerprint contract is introduced.

If a validate-only launcher diverges from canonical binding, report `UNMANAGED_CONFLICT` / broken launch-path state. Do not rewrite it automatically.

Longer term, duplicate launch authority should be reduced so helper launchers consume canonical config instead of shadowing it, but removing/changing that launcher contract is not implicit M5.9A authority.

Source-tree `target/release`, removed `mcp-server/<component>/...` paths, nested legacy bin paths, and divergent CLI overrides must be reported as drift/broken state.

## Gateway catalog verification

After reconcile/reload, verify the exact expected catalog rather than only an aggregate count.

The expected exact tool-name set must come from the trusted generated child configuration plus child MCP protocol discovery, not from a hard-coded count. The reconciler may use a temporary standalone Gateway probe, as M5.8 does, to derive/verify exact local catalog identity when the live tunnel-owned Gateway has no sideband inspection channel.

Do not claim that the live tunnel-owned Gateway or remote connected client was queried for an exact catalog unless such a channel/acknowledgement actually exists.


Required proof:

- Gateway MCP initialize succeeds;
- built-in Gateway tools are present;
- configured/enabled child set matches generated config;
- each enabled child is running and error-free;
- each child tool set matches its actual child `tools/list` filtered by configured allowlist/prefix policy;
- exposed aggregate tool-name set equals the expected set;
- a stable catalog fingerprint/generation is computed for diagnostics.

Tool count is useful telemetry but is not sufficient identity.

## Connected-client freshness boundary

Gateway can emit `notifications/tools/list_changed`, but Studio currently cannot prove that a remote ChatGPT/plugin session has refreshed its local callable catalog.

Therefore:

- local Gateway/catalog verification may become `SYNCHRONIZED`;
- end-to-end client freshness must remain `UNKNOWN` or `CLIENT_REFRESH_PENDING` unless a future protocol supplies an acknowledgement;
- Studio must not claim remote catalog freshness from local tool count alone;
- expose catalog generation/fingerprint so operators can compare reconnects and future M8 telemetry can correlate client refresh.

If the tunnel must be restarted to refresh the upstream control path, preserve prior running/stopped state and use bounded reconnect health verification.

## Repair transaction

For a safe managed drift:

1. capture byte-for-byte config snapshot and hashes;
2. render desired state into a candidate;
3. validate paths/schema/ownership and candidate semantics;
4. atomically replace only changed Fleet-owned generated files;
5. reload Gateway if `servers.d` changed;
6. restart tunnel only if its active binding/config changed and it was previously running;
7. run Gateway protocol + exact catalog verification;
8. re-run Fleet render checks;
9. persist/expose reconciliation result and catalog fingerprint;
10. remove rollback material only after success.

Failure after mutation must restore the complete captured config state, reload/restart affected owners as required, and verify the restored Gateway/catalog state.

## Startup and automatic behavior

M5.9A must provide the safe reconciliation primitive and startup drift detection.

A narrowly bounded startup self-repair may be enabled only for a proven `managed-safe` drift class after M5.12 fault-injection proves rollback/recovery. Unknown/unmanaged drift stays operator-gated.

Periodic unattended reconciliation, retry/backoff, maintenance-window policy and drift-loop circuit breaking belong to M7.

## API / realtime direction

Minimum direction:

```text
GET  /api/reconciliation
POST /api/reconciliation/check
POST /api/reconciliation/apply
```

Exact naming may change during implementation.

Public status should include:

- host id / host mode;
- synchronized/drifted/broken state;
- affected managed surfaces;
- safe-to-reconcile flag;
- last check/apply result;
- Gateway catalog fingerprint/generation;
- whether tunnel/Gateway restart is required;
- client freshness state without claiming an unobservable acknowledgement.

Do not expose secret values, internal arbitrary paths, or raw config contents by default.

## Tests

Hermetic tests must cover:

- synchronized runtime;
- stale tunnel Gateway path;
- stale `servers.d/exec.yaml`;
- run.sh/CLI override masking stale YAML;
- source-tree / `target/release` fallback path rejection;

- restart/reload rollback failure is explicit;

- no source/build toolchain dependency.

## M5.12 fault-injection proof

M5.12 must deliberately inject the incident class into an isolated source-less runtime fixture:

1. replace tunnel config with a legacy source-tree Gateway path;
2. drift one Gateway child config while leaving child binaries healthy;
3. verify Studio reports drift even when process health looks normal;
4. run reconcile;
5. verify canonical `bin/ + runtime/` paths are restored;
6. verify Gateway exact child/tool catalog;
7. verify tunnel running/stopped state preservation;
8. verify rollback by forcing a post-write catalog failure;
9. confirm no stale staging/config backup remains after success.

## Security requirements

- Reconciliation targets are server-controlled and root-confined.
- Symlink/special-file targets fail closed.
- Unknown local edits are not silently overwritten.
- No arbitrary command execution or browser-provided Fleet arguments.
- Snapshot/rollback material is permission-confined and cleaned after verified success.
- Secret-bearing fields/files require explicit preservation semantics.
- Automatic repair must have bounded retries and must never create restart/reconcile loops.

## Roadmap mapping

This submission is **M5.9A** in the implementation sequence and implements the runtime reconciliation work described under the M5 roadmap runtime-configuration-reconciliation section. Roadmap subsection numbering and implementation submission numbering are intentionally not 1:1; use the submission index in `README.md` as the execution order.

## Acceptance criteria

- Studio can detect Fleet-generated config drift independently of process health.
- Studio can explain which managed surfaces differ without exposing secrets.
- Safe managed drift can be repaired transactionally on a runtime-only host.
- Gateway reload/reconnect and exact tool-catalog restoration are verified before success.
- Divergent launch paths cannot silently mask stale canonical config.
- Unknown/unmanaged edits fail closed.
- Failed repair restores prior config/runtime state when rollback succeeds.
- M5.11 and M5.12 consume the reconciliation status/transaction surface.
- M7 has a clear safe primitive for later periodic unattended reconciliation.

## Out of scope

- general-purpose config editor;
- arbitrary user config merging;
- remote multi-host orchestration;
- claiming remote ChatGPT/plugin catalog refresh without an observable acknowledgement;
- periodic unattended reconcile policy (M7).

## Implementation evidence — 2026-09-19

Implemented after planning checkpoint `3c32545` on `feat/m5-runtime-distribution`.

### Delivered contracts

Fleet provides side-effect-free `fleetctl render-plan --host <host> --json`, merged to Fleet `main` in `6010727` with no-ff merge `9b8a9e1`. It returns exactly five Fleet-managed surfaces with trusted runtime-relative paths, exact base64 bytes, SHA-256 and lifecycle effects.

Studio adds `RuntimeReconciler` with:

- persisted managed baseline at `runtime/fleet/state/reconciliation.json`;
- deterministic `synchronized`, `managed_safe_drift`, `unmanaged_conflict`, and `broken` classification;
- legacy auto-adoption only when active managed bytes already match trusted desired bytes;
- explicit adoption that records current bytes without rewriting them;
- transactional snapshot, atomic replacement, rerender consistency check, verification, and rollback;
- validate-only handling for the non-Fleet `runtime/tunnel-client/run.sh`;
- Gateway config watcher handling without unnecessary tunnel restart;
- tunnel restart only when tunnel config changed and only when it was previously running;
- `studio_restart_required` without in-process Studio restart;
- exact local Gateway tool-name catalog fingerprinting from the standalone MCP protocol probe;
- explicit `unknown` / `refresh_pending` client freshness without claiming remote-client acknowledgement.

Public API:

```text
GET  /api/reconciliation
POST /api/reconciliation/check
POST /api/reconciliation/adopt
POST /api/reconciliation/apply
```

POST routes use the existing same-origin guard. `ReconciliationView` exposes logical status/effects/generation/fingerprint only; it omits raw config bytes and internal filesystem authority. Realtime publishes `reconciliation_changed`. Startup performs a drift check but never automatically applies repair.
