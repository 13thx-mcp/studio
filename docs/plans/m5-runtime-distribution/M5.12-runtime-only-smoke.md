# M5.12 — Source-less Runtime Host Proof, Rollback Drill and M5 Closure

## Goal

Prove the entire M5 architecture on a source-less runtime-host layout and close M5 only after bootstrap, inventory, update, reconnect, rollback, and recovery behavior are verified without local source/build toolchains.

## Prerequisites

- M5.1–M5.11 merged.
- Read `COMMON.md` and all prior handoffs.
- All release pipelines used by the smoke must already publish the required test versions/assets.

## Host strategy

Do not use Mirin until explicitly approved for this closure run if the user wants it preserved. A temporary isolated source-less fixture/root on Aira is acceptable for most automated/manual proof.

The final acceptance environment must intentionally omit project source dependencies from the runtime root.

## Minimum source-less layout

```text
mcp-server/
├── bin/
│   ├── rust-mcp-filesystem
│   ├── rust-mcp-git
│   ├── rust-mcp-exec
│   └── rust-mcp-gateway
│
└── runtime/
    ├── gateway/servers.d/
    ├── studio/
    ├── tunnel-client/
    └── fleet/
```

Depending on the final M5.10 Studio layout, use the actual versioned/self-update runtime structure.

The test environment must not rely on:

- `mcp-server/filesystem/` source;
- `mcp-server/git/` source;
- `mcp-server/exec/` source;
- `mcp-server/gateway/` source;
- `mcp-server/studio/` source;
- Rust/Cargo;
- Node/pnpm;
- `target/`;
- `node_modules/`.

## Bootstrap proof

Prove a clean runtime can be assembled from published releases plus host-local configuration:

1. Detect OS/architecture.
2. Fetch/verify/install project-owned release assets.
3. Fetch/verify/install official tunnel-client asset.
4. Install Fleet control bundle.
5. Generate/validate runtime Gateway/Studio/tunnel config.
6. Install/configure Studio service/launcher.
7. Start tunnel/Gateway/MCP/Studio as required.
8. Verify Studio inventory reports correct installed/running identities.

If M5 does not own first-install bootstrap automation yet, document exactly which steps remain manual; but the runtime operation itself must not require source compilation.

## Update proof

Exercise at least one real version transition per relevant transaction class. If only one public version exists, create controlled prerelease/test release versions or safe fixtures rather than pretending an update occurred.

Required classes:

- ordinary Rust MCP update while running;
- ordinary Rust MCP update while stopped;
- Gateway update with reconnect/catalog restoration;
- Fleet bundle update preserving host profile;
- tunnel-client check/update path (real update if a newer controlled/official version is available; otherwise force-reinstall integrity path plus rollback mechanics as supported);
- Studio self-update through external supervisor contract;
- runtime configuration reconciliation / Gateway catalog repair from M5.9A.

## Runtime drift / reconciliation drill

Deliberately reproduce the incident class inside an isolated source-less fixture:

1. install a valid canonical runtime and prove it synchronized;
2. change tunnel YAML to a legacy source-tree Gateway/config path;
3. add a correct helper/CLI override so process startup can still appear healthy;
4. drift at least one Gateway child config (for example Exec) from the active Fleet host profile;
5. prove Studio reports drift/broken state despite apparently healthy process state;
6. run the M5.9A reconciliation transaction;
7. prove canonical flat `bin_root` + `runtime_root` bindings are restored;
8. prove exact Gateway child/tool-name set and catalog fingerprint;
9. prove prior tunnel running/stopped state is preserved;
10. force a post-write catalog verification failure and prove config/runtime rollback;
11. verify unknown local edits are not silently overwritten.

If the upstream client provides no catalog-refresh acknowledgement, record local synchronization as proven and client freshness as unknown/pending rather than claiming end-to-end refresh.

## Rollback drill

Induce controlled failures after staging/activation where possible and prove:

- ordinary MCP health verification failure rolls back;
- Gateway failed activation/reconnect rolls back;
- Studio failed startup/health finalization rolls back through launcher contract;
- host-local config/profile remains intact;
- final inventory reflects the actual recovered version/state.

At least one rollback must use a genuinely activated bad/test build or deterministic verification failure path, not only a unit-test mock.

## Security/tamper drill

Verify runtime refuses:

- bad SHA-256;
- wrong architecture artifact;
- archive traversal entry;
- missing expected executable/package content;
- arbitrary release URL supplied by client/browser;
- update request for unknown component.

## Reboot/restart recovery

Where practical simulate or test process restart around:

- staged but not activated update;
- pending Studio self-update;
- completed activation awaiting finalization;
- stale update lock/transaction state.

Behavior must be deterministic and documented.

## End-to-end UI proof

Verify from Studio UI:

- runtime-only host mode visible;
- current/available/running/desired versions correct;
- update available/drift states correct;
- update transaction progress visible;
- reconnect recovery works for Gateway/Studio;
- rollback result visible;
- no source checkout is required for displayed truth or runtime actions.

## Soak / repetition

Run repeated update-check/inventory cycles and lifecycle operations long enough to catch obvious stale state or leaked temp staging directories.

At minimum inspect:

- staging cleanup;
- retained release policy;
- update locks;
- orphan processes;
- logs for secret leakage;
- disk growth behavior.

## Release preparation

Only after every M5 acceptance criterion passes:

- update Studio version/changelog as required for `v0.5.0`;
- run full release gates;
- perform security review checklist;
- prepare exact release commit according to repository policy;
- merge through normal no-ff workflow;
- create/push release tag only when release readiness is proven;
- verify GitHub release pipeline artifacts/checksums.

## M5 exit criteria

M5 is complete only when all of the following are true:

1. A source-less macOS host can operate Studio/Gateway/MCP/tunnel without source/build toolchains.
2. Studio reports trusted installed/running/desired/latest identities.
3. Project release and official tunnel release providers are verified and policy-confined.
4. Artifact download/checksum/safe extraction is proven against corrupt/malicious fixtures.
5. Ordinary MCP transactional update + rollback works.
6. Gateway update/reconnect/catalog verification + rollback works.
7. Fleet update preserves host profile/config.
8. Fleet-generated Gateway/tunnel/Studio runtime drift is detected and managed-safe drift can be transactionally reconciled with rollback.
9. Gateway catalog verification proves exact expected tool identity/set after reconciliation; client refresh is not falsely claimed when unobservable.
10. Studio self-update uses the documented external supervisor contract and can recover/rollback.
11. Updates/Fleet UI exposes accurate progress/drift/reconnect/reconciliation/error state.
12. Host-local config/secrets/state survive updates and safe reconciliation.
13. No unattended release auto-update or periodic unattended reconciliation is enabled yet.
14. Full backend/frontend/security/release gates are green.
15. Real end-to-end source-less smoke, reconciliation fault injection and rollback drill are recorded.
16. `v0.5.0` release artifacts can be produced reproducibly from source.

## Out of scope / next milestone

M5 does not close:

- SQLite historical persistence/audit (M6);
- unattended auto-update scheduling/policy (M7);
- advanced Gateway usage telemetry (M8);
- remote multi-host central control (post-v1.0 unless roadmap changes).
