# M5.5 — Artifact Download, Integrity Verification and Safe Staging

## Goal

Implement a reusable staging layer that downloads a selected release artifact, verifies integrity, safely extracts it, validates expected package structure, and produces an immutable staged artifact ready for later activation.

No active runtime installation may be modified in this submilestone.

## Prerequisites

- M5.1–M5.4 merged.
- Read `COMMON.md` and prior handoffs.
- Reuse proven fleet tunnel-updater behavior where appropriate.

## Scope

Implement:

- bounded HTTPS artifact download;
- checksum manifest download/read;
- SHA-256 verification;
- safe tar.gz extraction;
- safe zip extraction;
- release package structure validation;
- expected executable validation;
- executable permission normalization where archive formats lose mode bits;
- staged metadata recording;
- cleanup of failed/incomplete staging directories.

## Staging root

Use a dedicated runtime staging area outside active installation paths, for example beneath Studio runtime state. The exact path is an implementation decision but must:

- be server-controlled;
- be confined under trusted runtime root;
- not collide with active binaries/config;
- allow atomic move/activation later when filesystem semantics permit;
- be cleanable after failure/restart.

## Download requirements

- HTTPS only.
- Timeouts and bounded response sizes.
- Stream large artifacts rather than requiring unnecessary full in-memory buffering.
- Write to a temporary/staging file first.
- Compute SHA-256 over exact downloaded bytes.
- Checksum mismatch immediately invalidates the staged transaction.
- Never execute downloaded code during verification except narrowly defined binary `--version` validation when explicitly required and safely staged.

## Safe extraction requirements

Reject archive entries with:

- absolute paths;
- `..` traversal;
- paths escaping staging root after normalization;
- unsafe symlinks/hardlinks;
- special device nodes or unsupported entry types;
- duplicate paths if they could alter validation semantics.

For project tar.gz assets, validate the expected top-level package directory and expected binary name.

For official tunnel ZIP assets, validate expected runtime/cloudflared/manifest structure and restore executable bits before version checks where needed.

## Package validation

Project release package:

```text
<binary>-vX.Y.Z-<platform>/
├── <binary>
├── README.md      # optional by component policy
└── LICENSE        # optional by component policy
```

Studio package additionally requires matching dashboard files:

```text
mcp-studio-vX.Y.Z-<platform>/
├── mcp-studio
└── web/dist/...
```

Fleet package has its architecture-independent bundle contract.

Tunnel package follows upstream official structure.

Do not accept unexpected package layouts by searching recursively for “a binary that looks right”.

## Staged identity

Return/persist enough transient metadata for activation layers to know:

- component ID;
- version;
- provider/release identity;
- selected platform/asset;
- archive SHA-256;
- staging path;
- validated executable/package paths;
- verification timestamp/result.

## Failure recovery

A failed operation must:

- leave active installation unchanged;
- not leave a staged artifact marked valid;
- clean temporary partial downloads/extractions where safe;
- expose a typed failure reason suitable for M5.6/M5.11.

## Tests

Use local fixtures/mock HTTP.

Cover:

- successful tar.gz staging;
- successful zip staging;
- SHA mismatch;
- checksum entry missing;
- truncated download/archive;
- absolute/traversal archive path;
- symlink/hardlink escape;
- missing expected executable;
- duplicate/ambiguous package structure;
- wrong Studio package missing `web/dist`;

## Acceptance criteria

- A selected release asset can be safely staged and validated for every current packaging class.
- No active component is stopped, replaced, restarted, or otherwise mutated.
- Malicious/corrupt archives fail closed.
- Staged output has deterministic typed identity for later activation.
- Full backend gates and security-focused tests pass.

## Out of scope

- inventory public API;
- active installation;
- process lifecycle update transaction;
- rollback activation;
- UI.

## Implementation evidence — 2026-09-17

Implemented directly on `feat/m5-runtime-distribution` after M5.4. No active installation/update transaction behavior from M5.7+ was introduced.

### Staging contract

- Module: `src/update/staging.rs`.
- Entry point: `ArtifactStager::stage(provider, release, platform) -> StudioResult<StagedArtifact>`.
- Staging root is derived exclusively from trusted `ComponentCatalog::runtime_root()` as `<runtime_root>/.mcp-studio-staging`.
- Transactions are created as `.partial-*`; temporary ownership removes failed transactions automatically. Stager construction removes stale `.partial-*` directories from interrupted prior work.
- Successful transactions are atomically renamed to unique `ready-*` directories only after all verification succeeds. M5.5 exposes no mutation API for ready transactions.
- `StagedArtifact` serializes component/version/provider/release/platform identity, selected asset, exact archive SHA-256, final staging path, validated package root, validated executable paths, and verification timestamp. M5.7 later extends this persisted identity with SHA-256 values for each validated executable so apply-time TOCTOU revalidation can bind extracted bytes as well as the retained archive. The same object is atomically persisted as `staged.json`.
- Verified archive bytes and the checksum manifest remain inside the ready transaction for later activation/audit use.

### Download and integrity behavior

- Staging re-resolves trusted component/provider policy and calls the existing M5.4 `ReleaseProvider::select_asset()` exact selector.
- Selected asset URLs are revalidated as HTTPS GitHub release-download URLs beneath the trusted catalog owner/repository before retrieval.
- Artifact transport uses Reqwest/Rustls, HTTPS-only requests, five-second connect timeout, 120-second request timeout, GitHub-controlled redirect policy, fixed Studio User-Agent, and streaming writes.
- Compressed artifact download is capped at 256 MiB. SHA-256 is computed over the exact streamed bytes while writing the partial archive.
- Provider `checksum_manifest()` remains bounded by the M5.2/M5.3 256 KiB manifest cap. Staging requires a UTF-8 manifest with valid 64-hex SHA-256 records and exactly one entry matching the selected asset name.
- Missing/duplicate checksum entries, malformed checksum text, and digest mismatch fail before extraction.

### Safe extraction and package validation

- Both tar.gz and ZIP extraction cap entry count at 4,096 and total expanded regular-file bytes at 1 GiB.
- Absolute paths, parent traversal, ambiguous backslash separators, empty normalized paths, duplicate normalized paths, symlinks, hardlinks, device/special tar entries, and unsupported ZIP entry types fail closed.
- Files are created with create-new semantics inside a newly created extraction root; extraction never searches or writes an active install path.
- Project MCP tarballs require the exact `<binary>-v<version>-<platform>` top-level directory, exact expected binary, and only optional `README.md` / `LICENSE` siblings.
- Studio requires the exact top-level package root, `mcp-studio`, and `web/dist/index.html`; additional dashboard files must remain under `web/`.
- Fleet requires the exact current bundle structure (`VERSION`, `fleet.toml`, `README.md`, `scripts/fleetctl.py`, `hosts/mirin.example.toml` plus their directories), rejects extra bundle paths, and requires `VERSION` to equal the release semantic version.
- Official tunnel runtime-cloudflared ZIP is root-level and requires exactly `tunnel-client-runtime-cloudflared`, `cloudflared`, `cloudflared-manifest.json`, `LICENSE`, `NOTICE`, the release-specific license report, and matching SPDX document. The cloudflared manifest must be valid JSON with a non-empty version.
- Expected executables are normalized to executable permissions inside staging.
- Tunnel staging performs the narrowly scoped checksum-verified `tunnel-client-runtime-cloudflared --version` check with an empty environment and five-second timeout; the first reported version token must equal the release semantic version. Other downloaded component binaries are not executed during M5.5 verification.

### Failure/active-runtime guarantees

- Checksum, malformed archive, traversal/absolute path, duplicate path, symlink/hardlink, missing executable, and malformed Studio/package failure tests all complete without activation.
- A representative active-runtime marker remains byte-identical across checksum failure paths. Architecturally, `ArtifactStager` receives no active install destination and only creates descendants of the dedicated staging root.
- Failed staging does not create a `ready-*` directory or valid `staged.json`; partial directories are removed.
- No MCP/tunnel lifecycle call, active binary replacement, `current` symlink mutation, config/secret write, rollback action, or public update endpoint is present in M5.5.

### M5.6 / M5.7 carry-forward contract

M5.6 may surface staging/inventory state but must not expose internal download/install authority. M5.7 may accept a `StagedArtifact` only after independently resolving the same trusted component and should re-check that `staged.json`, staging path confinement, selected identity, archive digest, package root, and validated executable paths remain internally consistent immediately before activation to reduce TOCTOU risk. It can assume M5.5 already verified the release-provider identity, exact platform asset selection, manifest SHA-256, safe extraction, current package structure, executable permissions, and (for tunnel) staged binary release version. M5.7 still owns stop-state preservation, rollback preparation, atomic/destructive activation, health verification, recovery, and cleanup/retention of ready staging material.
