# M5.11 — Updates / Fleet UI and Realtime Transaction Surfaces

## Goal

Add the operator-facing Updates/Fleet UI using the backend inventory/update/reconciliation APIs and transaction state implemented in M5.1–M5.10, including M5.9A runtime reconciliation.

## Prerequisites

- M5.1–M5.10 merged.
- Read `COMMON.md` and prior handoffs.
- Backend API/state contracts must be treated as current source of truth.

## Scope

Add an Updates/Fleet area to the Studio dashboard that shows, per component:

- component name/class;
- release provider/source;
- installed version;
- running version;
- desired version;
- latest available version;
- OS/architecture;
- update/drift state;
- integrity/check status where available;
- runtime state;
- last update result/time;
- restart required/pending activation state;
- source-present vs runtime-only host mode;
- Fleet-generated runtime-config reconciliation state;
- Gateway catalog fingerprint/generation and client-refresh-pending state where applicable.

## Operator actions

Support only actions already proven safe by backend submilestones:

- check for updates;
- prepare/stage a specific approved version where supported;
- apply update;
- rollback when rollback material exists;
- resume/query pending Studio self-update state;
- check runtime configuration drift;
- apply a server-approved managed-safe reconciliation plan;
- inspect unmanaged-conflict / client-refresh-pending state.

Do not expose unattended auto-update controls in M5.

## UX requirements

Before any mutation, show clearly:

- target component;
- current installed/running version;
- target version;
- expected restart/reconnect impact;
- whether rollback is available;
- whether the component is currently running;
- special warning for Gateway or Studio updates that may reconnect the UI/control path.

Progress should map to backend transaction states rather than display a fake percentage.

Examples:

```text
Checking release
Downloading
Verifying checksum
Staging
Stopping component
Activating
Restarting
Verifying health
Rolling back
Complete
```

## Reconnect behavior

Gateway and Studio updates may interrupt the browser connection.

The UI must:

- retain transaction ID locally where appropriate;
- reconnect using existing WebSocket/reload behavior;
- refetch transaction/inventory state after reconnect;
- distinguish expected reconnect from final failure;
- avoid submitting duplicate apply actions after reconnect.

## Error surfaces

Display actionable typed failures such as:

- release unavailable;
- unsupported platform;
- checksum mismatch;
- package invalid;
- component stop failure;
- activation failure;
- health verification failure;
- rollback succeeded after failed update;
- rollback failed;
- external Studio launcher unavailable.

Do not expose sensitive raw HTTP headers, tokens, internal secret paths, or arbitrary filesystem details.

## Fleet / drift view

Provide a host summary with:

```text
host id
host mode: development | runtime-only
platform
architecture
component drift summary
last update check
components requiring restart
components broken/unknown
```

M5 is local-host only; do not invent remote multi-host control yet.

## Implementation evidence — 2026-09-19

Implemented on `feat/m5-runtime-distribution` after M5.10.

### Final UI contract

The dashboard now includes an `Updates / Fleet` area backed only by existing browser-safe backend contracts:

```text
GET  /api/updates
POST /api/updates/check
POST /api/updates/{component}/prepare
POST /api/updates/{component}/apply
GET  /api/update-transactions/{transaction_id}

GET  /api/reconciliation
POST /api/reconciliation/check
POST /api/reconciliation/apply
```

Realtime consumes `updates_changed`, `update_transaction`, and `reconciliation_changed`.

Per component the UI shows class/provider, installed/running/desired/latest versions, platform, host mode, installation health, drift, release-check state/time, runtime state, and current transaction result. The host/Fleet summary shows local host identity, runtime-only/source-present mode, platform, update count, restart drift, broken count and last release-check time.

Prepare/apply confirmations show current installed/running identity, target version, runtime state, restart/reconnect impact, and backend rollback semantics. Transaction progress maps directly to backend phases rather than a fake percentage.

Gateway and Studio control-path transactions display an expected-reconnect warning. The browser persists every non-terminal `(transaction_id, component)` reference and refetches all pending transaction IDs on initial load and each realtime reconnect. Terminal state removes only its own persisted reference.

The reconciliation view exposes managed-safe drift, unmanaged conflict, affected logical surfaces, generation, local Gateway catalog fingerprint, client `refresh_pending`, lifecycle effects and sanitized errors. Apply is enabled only when the backend reports `managed_safe_drift` and `safe_to_reconcile=true`; unmanaged conflict remains inspect-only.

Tunnel shows inventory/latest-release visibility but no Apply action because the current backend has no tunnel activation manager. The UI also exposes no standalone rollback button because rollback is automatic backend transaction behavior and there is no public manual rollback endpoint.

### Release-check responsiveness

M5.11 changed `InventoryService::check()` from sequential component lookups to concurrent fan-out over the closed eight-component catalog. Provider/catalog policy, previous-latest preservation, sanitized errors and final inventory ordering are unchanged.

The isolated runtime-only smoke measured the eight-component check at approximately 0.78 seconds on Aira instead of exceeding the prior sequential smoke budget.
