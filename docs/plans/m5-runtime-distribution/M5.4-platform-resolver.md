# M5.4 — Platform / Architecture Resolver and Asset Selection

## Goal

Provide one strict, tested platform-resolution layer that maps the current host to supported release artifact identity and rejects ambiguous/unsupported assets.

## Prerequisites

- M5.1–M5.3 merged.
- Read `COMMON.md` and prior handoffs.

## Required initial targets

```text
darwin-amd64
darwin-arm64
```

Normalize at least:

```text
Darwin → darwin
x86_64 / amd64 → amd64
arm64 / aarch64 → arm64
```

Unsupported OS or architecture must fail closed.

## Scope

Implement typed platform identity and deterministic asset selection for:

- project-owned Rust MCP/service tar.gz releases;
- architecture-independent Fleet bundle;
- official tunnel-client runtime-cloudflared zip releases.

The resolver should operate on typed release asset metadata from providers rather than perform HTTP calls itself.

## Selection rules

For each component/provider:

- derive the expected asset name from trusted component metadata + release version + platform;
- require exactly one matching asset;
- reject zero matches;
- reject duplicates/ambiguity;
- never select a “closest” architecture;
- never silently fall back from arm64 to amd64 or vice versa;
- architecture-independent components must explicitly declare that property rather than bypass selection accidentally.

## Host detection

Host detection must be isolated/testable. Avoid scattering direct `uname`/environment parsing throughout update code.

Suggested conceptual API:

```text
HostPlatform::detect()
normalize_os(...)
normalize_arch(...)
select_asset(component, release, platform)
```

## Security / correctness requirements

- Asset names derive from trusted server-side component contracts.
- No browser-supplied asset filename.
- Unsupported platforms produce explicit errors.
- Do not rely only on filename substring containment when an exact expected name is available.
- Keep future Linux support extensible but do not claim support without release artifacts + tests.

## Tests

Cover at least:

- Darwin x86_64 → darwin-amd64;
- Darwin arm64 → darwin-arm64;
- alias normalization;
- unsupported OS;
- unsupported architecture;
- exact project Rust asset selection;
- exact Studio asset selection;
- Fleet architecture-independent selection;
- exact official tunnel zip selection;
- missing asset;
- duplicate matching asset;
- similar-but-wrong architecture/version filenames rejected.

## API/UI

No public update API/UI required yet. Internal platform identity may later be surfaced by M5.6.

## Acceptance criteria

- Every current release component can deterministically resolve an expected asset for supported macOS platforms.
- Unsupported/ambiguous states fail closed with useful typed errors.
- Resolver has no network or filesystem mutation side effects.
- Full backend quality gates pass.

## Out of scope

- downloads;
- checksum verification;
- extraction;
- activation;
- rollback;
- UI.

## Completion handoff

Record the exact platform and asset-selection APIs M5.5 should call and any component-specific packaging differences.

## Implementation evidence — 2026-09-17

Implemented directly on the canonical `feat/m5-runtime-distribution` integration branch after M5.3, without creating a submilestone branch and without adding M5.5 download/staging behavior.

### Platform API

- Module: `src/update/platform.rs`.
- `HostPlatform::detect() -> StudioResult<HostPlatform>` isolates production host detection using Rust target OS/architecture identity.
- `HostPlatform::from_raw(os, arch)` is the deterministic test seam.
- `HostPlatform::platform() -> Platform` returns the typed M5.1 platform identity.
- `normalize_os(value)` accepts `Darwin`/`darwin` and Rust `macos`, all mapping to `OperatingSystem::Darwin`.
- `normalize_arch(value)` maps `x86_64`/`amd64` to `Architecture::Amd64` and `arm64`/`aarch64` to `Architecture::Arm64`.
- Unsupported OS/architecture values fail closed through typed `UnsupportedOperatingSystem` / `UnsupportedArchitecture` errors. Linux is intentionally not claimed as supported.

### Trusted packaging / asset-selection API

- `ComponentPolicy` now carries server-owned `ReleaseAssetPolicy { stem, kind }`. This extends M5.1 policy without changing browser mutation/request authority or the `ReleaseProvider` interface.
- `ReleaseAssetKind::{PlatformTarGz, ArchitectureIndependentTarGz, PlatformZip}` makes architecture dependence explicit.
- `expected_asset_name(component, release, platform)` derives the one exact trusted archive filename.
- `select_release_asset(component, release, platform)` requires exactly one equality match in typed provider metadata and rejects release/component mismatch, zero exact matches, or duplicate exact matches.
- Both `ThirteenthXReleaseProvider::select_asset()` and `OpenAiTunnelReleaseProvider::select_asset()` preserve the existing M5.1 trait and delegate to the shared resolver after catalog policy re-resolution.

Current exact contracts:

- Filesystem: `rust-mcp-filesystem-v<version>-<platform>.tar.gz`.
- Git: `rust-mcp-git-v<version>-<platform>.tar.gz`.
- Exec: `rust-mcp-exec-v<version>-<platform>.tar.gz`.
- Gateway: `rust-mcp-gateway-v<version>-<platform>.tar.gz`.
- Blender: `rust-mcp-blender-v<version>-<platform>.tar.gz`.
- Studio: `mcp-studio-v<version>-<platform>.tar.gz`.
- Fleet: `mcp-fleet-v<version>.tar.gz`, explicitly `ArchitectureIndependentTarGz`.
- Tunnel: `tunnel-client-runtime-cloudflared-v<version>-<platform>.zip`.

There is no amd64/arm64 fallback, substring matching, closest-name matching, or accidental selection of SPDX/license/source/full-client sidecars.

### M5.5 carry-forward contract

M5.5 should call `HostPlatform::detect()?.platform()` once for the host, then use the provider's existing `select_asset(&release, platform)` method (or `select_release_asset` only when it already owns a trusted `ComponentPolicy`) before downloading bytes. The returned `ReleaseAsset` is an exact trusted-name candidate but is not yet integrity-verified. M5.5 must fetch that asset and `checksum_manifest()`, verify the exact `SHA256SUMS.txt` entry, enforce size/resource bounds, safely extract `.tar.gz` versus tunnel `.zip` according to `ReleaseAssetKind`, reject traversal/absolute paths/unsafe links, validate expected archive structure, and for tunnel verify the staged `tunnel-client-runtime-cloudflared` version before any activation.
