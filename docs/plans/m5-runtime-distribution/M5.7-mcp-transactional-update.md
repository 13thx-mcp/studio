# M5.7 — Transactional Rust MCP Update and Rollback

## Goal

Implement the first active update transaction: safely replace one flat Rust MCP binary using a verified staged release, preserve prior runtime state, restart only when appropriate, health/protocol verify the new binary, and roll back on failure.

## Prerequisites

- M5.1–M5.6 merged.
- Read `COMMON.md` and all prior handoffs.
- Staging layer guarantees from M5.5 must be explicit and trusted.

## Initial targets

Implement the generic MCP transaction for flat `bin_root` components such as:

```text
rust-mcp-filesystem
rust-mcp-git
rust-mcp-exec
```

Blender may use the same mechanism if its release/provider configuration exists; do not expand scope unnecessarily.

Gateway is excluded here because M5.8 owns its control-path-specific behavior.

## Transaction semantics

Required sequence:

```text
verified staged artifact
→ acquire per-component update lock
→ capture pre-update state
→ prepare rollback material
→ stop target only if currently running
→ atomically activate new binary in flat bin root
→ start target only if it was running before
→ protocol/health verification
→ mark success/current
→ retire transaction lock
```

If verification fails:

```text
stop failed new runtime if necessary
→ restore previous known-good binary atomically
→ restore previous running/stopped state
→ verify rollback runtime when previously running
→ expose rollback outcome
```

## Pre-update state

Capture at least:

- component ID;
- current installed version/checksum;
- current running/stopped state;
- current executable identity/path;
- staged target version/checksum;
- rollback artifact/path identity.

Do not infer “was running” from desired policy; query actual supervisor/runtime state.

## Atomic activation

The flat bin root is shared by multiple MCP binaries. Replace only the target binary. Use same-filesystem atomic rename/replacement semantics where possible.

Never mutate unrelated files in `bin_root`.

Preserve executable permissions.

## Update locking

Prevent concurrent update operations that could race on the same component. Define whether unrelated components may update concurrently; conservative serialization is acceptable initially if clearly implemented/tested.

A duplicate apply request should return a conflict/state error rather than launch a second transaction.

## Lifecycle integration

Use existing Studio supervisor APIs/state machine rather than spawning/killing MCPs independently from update code.

An MCP stopped before update must remain stopped after success.

An MCP running before update should be restarted and verified after activation.

Do not auto-start disabled MCPs.

## Health/protocol verification

Use a component-appropriate verification that proves the new MCP executable can initialize/start correctly. Prefer protocol-level MCP initialize/catalog validation when practical rather than only checking process existence.

Define bounded verification timeouts.

## API

Add mutation endpoints for MCP update preparation/apply/rollback as needed by the architecture. Public requests should contain a component ID and approved/policy-resolved version only; never arbitrary paths/URLs.

Same-origin mutation protection must apply.

## Realtime/logging

Emit transaction state/progress events suitable for M5.11:

```text
preparing
stopping
activating
starting
verifying
rolling_back
completed
failed
```

Logs should include transaction ID/component/version but no secret headers/tokens.

## Tests

Automated tests must cover:

- update stopped MCP → remains stopped;
- update running MCP → restart succeeds;
- activation atomicity;
- unrelated flat-bin files untouched;
- target binary missing before update;
- stop failure;
- activation failure;
- new binary fails verification → rollback succeeds;
- rollback fails → explicit ROLLBACK_FAILED;
- duplicate/concurrent update rejected;
- disabled component remains disabled/stopped;
- checksum/staging-invalid input cannot reach activation;
- interrupted/failed transaction leaves deterministic recoverable state.

Add a real-workspace smoke on Aira using a safe fixture/version transition strategy. Do not damage the currently connected control path.

## Security requirements

- Activation accepts only a previously verified staged artifact object/ID, not a browser path.
- Revalidate staging identity immediately before activation to reduce TOCTOU risk.
- Rollback data must be server-controlled.
- No shell commands built from browser strings.
- Path stays confined to configured flat bin root and exact component binary name.

## Acceptance criteria

- Generic non-Gateway Rust MCP update transaction works for running and stopped components.
- Post-activation verification is mandatory.
- Failed verification restores last-known-good state when rollback succeeds.
- Only target component runtime is affected.
- API/realtime state exposes useful deterministic progress/failure.
- Full backend gates and lifecycle/update smoke pass.

## Out of scope

- Gateway update;
- Fleet update;
- Studio self-update;
- unattended auto-update;
- final Updates UI.

## Completion handoff

Record transaction/rollback contracts, update-lock ownership, verification mechanism, and which generic code M5.8 should reuse versus override.

## Implementation evidence — 2026-09-18

Implemented directly on the canonical `feat/m5-runtime-distribution` branch after M5.6. Gateway remains explicitly excluded for M5.8; Studio/Fleet/tunnel update paths were not added.

### Transaction/API contract

- New module: `src/update/transaction.rs`; entry point: `McpUpdateManager`.
- Generic targets are project-owned `McpBinary` components except `gateway`: Filesystem, Git, Exec, and Blender when their trusted release exists. Non-MCP targets and Gateway fail before staging/activation.
- `POST /api/updates/{component}/prepare` accepts only `{ "version": "MAJOR.MINOR.PATCH" }`. It requires a newer version than the current runtime-artifact identity, resolves the trusted `13thx-mcp` release/provider/platform, stages through M5.5, and returns a server-generated transaction ID.
- `POST /api/updates/{component}/apply` accepts only `{ "transaction_id": "txn-..." }`; browser paths, URLs, repositories, executable names, checksums, and extra authority fields are rejected.
- `GET /api/update-transactions/{transaction_id}` returns process-lifetime browser-safe progress.
- Prepare/apply retain same-origin mutation protection. Transaction/release/staging errors exposed by HTTP and realtime are mapped to safe categories rather than raw internal paths/URLs.
- Realtime adds `update_transaction` events with `preparing`, `staged`, `stopping`, `activating`, `starting`, `verifying`, `rolling_back`, `completed`, `failed`, and `rollback_failed`.

### Staging/TOCTOU revalidation

- M5.7 extends `StagedArtifact` with SHA-256 identities for each validated executable.
- `ArtifactStager::load_ready(transaction_id)` accepts only safe server-generated `ready-*` IDs, rejects symlink/non-directory staging roots, re-confines metadata/package/executable paths to the trusted staging root, revalidates provider/release/asset identity, re-hashes the retained verified archive, and re-hashes each extracted executable.
- Preparation stores an in-memory fingerprint containing target version, provider, asset name, archive digest, and executable digests. Apply requires the reloaded ready artifact to match that fingerprint exactly before any lifecycle stop.
- Apply also re-probes installed identity and requires it to equal the preparation source-version snapshot.
- Tests prove both archive tampering and extracted-executable tampering fail before Supervisor stop.

### Lock/lifecycle/activation contract

- Locking is per component. A duplicate operation for one component returns conflict; unrelated components may hold independent update locks.
- Actual running/stopped/enabled state is queried from the existing `Supervisor`; desired policy is never used to infer `was_running`.
- The registry executable must canonicalize to the exact catalog-derived target binary. The target must be a regular non-symlink file directly under configured `bin_root`.
- A missing target fails with no activation because there is no rollback baseline.
- Before stopping/replacing anything, Studio copies the old target to a create-new sibling rollback partial, preserves permissions, fsyncs it, computes SHA-256, writes/fsyncs a checksum sidecar, then finalizes rollback material by rename.
- If the MCP was running, only that MCP is stopped through Supervisor. Stopped or disabled MCPs are not auto-started.
- Activation copies the staged binary into a create-new sibling activation scratch file on the same filesystem, fsyncs it, preserves executable permissions, and atomically renames it over only the target binary. Unrelated flat-bin files are untouched.
- A previously running/enabled MCP is restarted through Supervisor after activation.

### Verification and rollback

- Mandatory binary verification executes the activated binary with `--version`, empty environment, kill-on-drop, and a five-second timeout, requiring exact semantic target version.
- For a previously running MCP, Supervisor must report `Running` immediately after restart and after a bounded 400 ms health window.
- The current Supervisor does not expose an MCP JSON-RPC stdin request/response channel, so M5.7 does **not** claim protocol-level MCP `initialize` verification. This is documented rather than creating a second process-control path.
- Activation, restart, or verification failure enters automatic rollback. A newly started failed runtime is stopped if necessary, rollback bytes and checksum sidecar are revalidated, and the old binary is atomically restored.
- If the MCP was previously running/enabled, rollback restarts it. Rollback success additionally verifies the restored source semantic version and the same bounded running-health window.
- Rollback failure becomes explicit `rollback_failed`; no false success is emitted.
- Successful transactions update the process-local desired inventory to the activated version only after verification and remove rollback material.

### Interruption/recovery behavior

- On manager construction, clearly disposable stale `.mcp-studio-activate-*` files and `.mcp-studio-rollback-*.partial` files are removed from trusted `bin_root`.
- Finalized rollback binaries/checksum sidecars are deliberately preserved: after a host/process interruption they may be the only known-good recovery material. M5.7 does not pretend to auto-complete an interrupted transaction without persisted transaction state.

### M5.8 carry-forward contract

M5.8 should reuse: trusted prepare/release/staging, `ArtifactStager::load_ready` hash/path revalidation, preparation fingerprints, per-component lock semantics, rollback material/checksum helpers, same-directory copy+rename activation primitives, safe transaction DTO/realtime phases, semantic binary verification, and the concept of restoring pre-update lifecycle state. M5.8 must **not** route Gateway through the generic `McpUpdateManager::validate_target` path or treat it as an ordinary child MCP restart. Gateway owns the Studio control path, so M5.8 must define a continuity-safe handoff/restart strategy and its own health proof while preserving the same browser authority and rollback invariants.
