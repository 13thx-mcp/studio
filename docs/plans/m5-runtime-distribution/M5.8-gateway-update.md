# M5.8 — Gateway Update, Reconnect and Child-Catalog Verification

## Goal

Implement a Gateway-specific update transaction that reuses the generic verified staging/activation machinery while accounting for Gateway's role in the active MCP control path.

## Prerequisites

- M5.1–M5.7 merged.
- Read `COMMON.md` and prior handoffs.
- Generic transaction/rollback mechanism from M5.7 must be stable.

## Why Gateway is special

Gateway owns the connection between tunnel/client traffic and child MCPs. Updating it can temporarily interrupt the very control path used by the current session.

Do not treat Gateway as an ordinary child MCP restart.

## Runtime contract

Current runtime layout:

```text
bin/rust-mcp-gateway
runtime/gateway/servers.d/
```

Generated `servers.d` is host-local runtime config and must survive Gateway release update unchanged unless a separately validated config migration is explicitly required.

## Transaction sequence

Suggested sequence:

```text
verified staged Gateway artifact
→ capture active Gateway/runtime catalog state
→ prepare rollback binary
→ validate existing generated config
→ stop/reload Gateway through owned runtime contract
→ atomically replace only bin/rust-mcp-gateway
→ restart/reconnect Gateway
→ wait for Gateway readiness
→ verify configured child catalog restored
→ verify expected enabled/running child health
→ verify tool catalog / protocol initialize
→ complete
```

On failure, rollback binary and reconnect using previous Gateway version.

## Reconnect semantics

A transient disconnected/restarting state is expected during activation and must not be reported as permanent failure prematurely.

Define bounded phases such as:

```text
GATEWAY_STOPPING
GATEWAY_RESTARTING
GATEWAY_RECONNECTING
GATEWAY_CATALOG_VERIFYING
```

The browser/UI should eventually be able to distinguish intentional update reconnect from crash/failure.

## Child catalog verification

After restart verify at least:

- Gateway process/protocol initializes;
- generated config directory is loaded;
- configured enabled children are visible;
- child startup failures are surfaced;
- expected tool catalog is non-empty/consistent with current config policy;
- no config path has silently fallen back to source-tree/nested-bin locations.

Do not hard-code one tool count forever if the catalog is expected to evolve; verify against current configured/expected metadata where feasible.

## Tunnel interaction

The secure tunnel may spawn/manage Gateway in the current deployment path. Inspect the actual ownership relationship before implementing stop/start semantics.

The update design must avoid two supervisors fighting over Gateway ownership.

If tunnel restart is required to activate a Gateway update in the current architecture, make that dependency explicit and minimize disruption. Do not silently restart tunnel if not required.

## API/realtime

Use the common update API/state model but expose Gateway-specific reconnect/catalog phases where useful.

If the API call connection itself can be interrupted during activation, define idempotent transaction IDs and post-reconnect status recovery so the UI can query the final result.

## Tests

Cover:

- successful Gateway update;
- generated `servers.d` preserved byte-for-byte;
- child catalog restored;
- one child fails after new Gateway start;
- Gateway binary verification fails → rollback;
- reconnect timeout → rollback/failure;
- duplicate apply rejected;
- transaction result recoverable after client reconnect;
- tunnel/Gateway ownership conflict prevention;
- old Gateway restored and functional after failed new activation.

Run a real Aira smoke with care not to strand the connected session; plan reconnect explicitly.

## Security requirements

- Exact trusted Gateway binary path only.
- Runtime config stays server-controlled.
- No arbitrary config-dir path from browser input.
- Rollback must preserve existing host-local config.
- Reconnect/status endpoints must not leak tunnel secrets.

## Acceptance criteria

- Gateway can update from verified release artifact without losing host runtime config.
- Intentional reconnect state is deterministic/recoverable.
- Child catalog health is verified before success.
- Failed activation can restore previous Gateway and connection path.
- Backend gates and reconnect smoke pass.

## Out of scope

- Fleet control bundle update;
- Studio self-update;
- unattended rollout;
- multi-host orchestration.

## Completion handoff

Document actual Gateway/tunnel ownership semantics, reconnect transaction behavior, child-catalog verification criteria, and prerequisites M5.9/M5.10 must preserve.

## Implementation evidence — 2026-09-18

Implemented directly on the canonical `feat/m5-runtime-distribution` branch after M5.7. The implementation keeps Gateway outside the generic `McpUpdateManager` lifecycle path and preserves Fleet/Studio/tunnel-update scope for later submissions.

### Actual Gateway/tunnel ownership contract

Inspection of the deployed Aira runtime and Fleet renderer confirmed that Gateway is not spawned by Studio's ordinary MCP `Supervisor`. `runtime/tunnel-client/config.yaml` owns the `main` Gateway process through an MCP command of the form:

```text
<bin_root>/rust-mcp-gateway --config-dir <runtime_root>/gateway/servers.d
```

The Fleet renderer emits the same ownership shape. M5.8 therefore treats `TunnelSupervisor` as the production Gateway process owner and never creates a competing Studio Gateway supervisor.

`TunnelSupervisor::validate_gateway_binding` now parses the server-owned tunnel YAML and requires exactly one `main` MCP command whose Gateway executable and `--config-dir` canonicalize to the catalog-derived flat Gateway binary and trusted `runtime/gateway/servers.d`. Browser input cannot choose either path.

### Gateway transaction contract

- New module/entry point: `src/update/gateway.rs` / `GatewayUpdateManager`.
- Existing update API remains the surface. `POST /api/updates/gateway/prepare` and `/apply` dispatch to the Gateway-specific manager; generic non-Gateway components still dispatch to M5.7 `McpUpdateManager`.
- `GET /api/update-transactions/{id}` can recover either generic-MCP or Gateway transaction state after a browser reconnect.
- Preparation uses the trusted project release provider, M5.4 platform resolver, M5.5 verified staging, executable/archive hashes, and M5.7 preparation fingerprint. Target version must be newer than the installed Gateway runtime identity.
- Apply re-probes the installed source version and re-loads the server-owned `ready-*` artifact before control-path mutation.
- Gateway uses its own transaction lock, so duplicate Gateway prepare/apply requests conflict.

### Generated config and child-path preservation

Before stopping a running owner, M5.8 captures `runtime/gateway/servers.d` as a closed snapshot:

- regular non-symlink files only;
- bounded file count and per-file size;
- SHA-256 for every file;
- parsed child name/enabled/command metadata;
- duplicate child names rejected;
- at least one configured child required.

Known managed child names (`filesystem`, `git`, `exec`, `blender`) must have a command that canonicalizes to the corresponding catalog flat-bin target. This prevents silent fallback to source-tree or nested-bin executables. The snapshot is re-captured after new-Gateway probing and during rollback verification; file bytes and child metadata must remain unchanged. No release archive writes `servers.d`.

### Activation and reconnect sequence

For a stopped tunnel owner:

```text
verified staged Gateway
→ validate tunnel binding + servers.d
→ prepare rollback
→ atomic Gateway binary activation
→ standalone Gateway protocol/catalog probe
→ complete while tunnel remains stopped
```

For a running tunnel owner:

```text
verified staged Gateway
→ validate tunnel binding + servers.d
→ prepare rollback
→ GatewayStopping: stop tunnel through TunnelSupervisor
→ atomic Gateway binary activation
→ GatewayCatalogVerifying: standalone protocol/catalog probe
→ GatewayRestarting: start tunnel through TunnelSupervisor
→ GatewayReconnecting: bounded wait through intentional transitional state
→ require stable Running health window + exact binding
→ complete
```

Gateway-specific phases are added to the common browser-safe transaction DTO/realtime event stream: `gateway_stopping`, `gateway_restarting`, `gateway_reconnecting`, and `gateway_catalog_verifying`. `Starting`/`Stopping` tunnel states during intentional reconnect are not treated as immediate permanent failure; production reconnect is bounded by a 10-second timeout and a subsequent 800 ms stable-running window.

### Gateway protocol and child-catalog verification

M5.8 adds an RMCP client probe that launches the selected Gateway binary as a temporary standalone stdio MCP server with the trusted `servers.d` and an empty environment. Success requires:

- MCP initialize handshake succeeds within the bounded probe timeout;
- `tools/list` succeeds;
- built-in `gateway_list_servers`, `gateway_reload`, and `gateway_set_server_enabled` tools exist;
- `gateway_list_servers` returns non-error structured content;
- configured and enabled child counts match the pre-update config snapshot;
- every enabled configured child is present, `running=true`, and has no error;
- no configured child reports an error;
- exposed child tools are non-zero when enabled children exist;
- the generated `servers.d` snapshot remains unchanged.

This gives Gateway a stronger protocol/catalog proof than the generic M5.7 `--version` + Supervisor-health verification.

### Rollback and failure semantics

Activation, new-Gateway protocol/catalog failure, tunnel restart failure, reconnect timeout, reconnect terminal state, reconnect health failure, binding mismatch, or generated-config mutation cannot be marked successful. After destructive activation the manager enters rollback:

- stop the newly started/transitional tunnel owner when necessary;
- validate and atomically restore M5.7 checksum-protected rollback bytes;
- verify restored source semantic version;
- run the restored Gateway through the same standalone MCP initialize/tools/child-catalog proof;
- verify `servers.d` stayed byte-for-byte unchanged;
- if the tunnel was previously running, restart it and require the same bounded reconnect + stable-running proof;
- if it was previously stopped, leave it stopped.

A failure anywhere in rollback becomes explicit `rollback_failed`.

### Acceptance criteria

- [x] Gateway has a dedicated verified-release update transaction respecting actual tunnel ownership.
- [x] Generated `servers.d` is server-controlled and verified byte-for-byte unchanged.
- [x] Known managed child commands must remain on trusted flat-bin paths.
- [x] Replacement and restored Gateway binaries must pass MCP initialize, built-in tool, child health, and tool-catalog verification.
- [x] Running owner reconnect is explicit, bounded, queryable after reconnect, and stable-running verified; stopped owner stays stopped.
- [x] Failed activation/catalog/reconnect restores the prior Gateway/control-path state when rollback succeeds; rollback failure is explicit.
- [x] Browser requests cannot provide Gateway/config/release authority or tunnel secrets.
- [x] Backend gates and a safe real Aira protocol/catalog smoke pass.

### M5.9 / M5.10 carry-forward

M5.9 and M5.10 must preserve the authority pattern established here: update APIs accept typed policy identity/transaction IDs, active host-local config is never overwritten by release archives, staged bytes are revalidated immediately before activation, lifecycle ownership is explicit, and success requires a component-appropriate post-activation proof. They may reuse M5.7 staging/rollback primitives and the common transaction DTO/realtime phases, but should not reuse Gateway's tunnel ownership assumptions for Fleet or Studio. Studio self-update still requires an external launcher/supervisor contract as required by `COMMON.md`.
